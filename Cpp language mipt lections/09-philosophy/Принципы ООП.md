## Базовые понятия
- Контекст инкапсулирует данные и охраняет инварианты.
- Контекст реализует интерфейс (для типов в `C++` через наследование интерфейса)
- Производный контекст расширяет базовый (для типов в `C++` через наследование реализации)
- Если контексты это типы, производный контекст связан с базовым дополнительными соотношениями (частное/общее, быть частью и подобными)
- Если несколько типов реализуют общий интерфейс, вызовы их методов через этот интерфейс полиморфны.

`UML` это средство описания, которым можно описать систему абсолютно любую, в том числе, сколь угодно плохую.

`Software` имеет анлийский корень `soft`, означающий нечто, что легко изменять. Но очень часто у нас вместо куска пластелина в руках некая засохшая субстанция с гвоздями.

Первый шаг к хорошему коду - это **легко изменяемый** код.
Собственно, отсюда вытекает, что характеристикой плохого кода является трудность в его расширении, эволюции.

Люди много думали и придумали ряд принципов для написания этого хорошего кода, ну или по крайней мере хорошо расширяемого кода.
# Принципы `SOLID`
1. **`SRP`** - `single responsibility principle`
   *Каждый контекст должен иметь только одну ответственность*
2. **`OCP`** - `open-close principle`
   *Каждый контекст должен быть закрыт для изменения и открыт для расширения*
3. **`LSP`** - `Liskov substitution principle`
   *Частный класс должен свободно замещать общий во всех контекстах, который подразумевает связь между ними.*
4. **`ISP`** - `interface separation principle`
   *Тип не должен зависеть от тех интефейсов, которые он не использует*
5. **`DIP`** - `dependency inversion principle`
   *Высокоуровневые классы не должны зависеть от низкоуровневых*

```cpp
#include <algorithm>
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

using Screen = std::ostream;

struct Vector3D {
  int x, y, z;
};

struct Polygon3D {
  std::vector<Vector3D> vs;
  Polygon3D(std::initializer_list<Vector3D> il) : vs(il) {}
};

void draw(int x, Screen &out, size_t position) {
  out << std::string(position, ' ') << x << "\n";
}

void draw(Vector3D v, Screen &out, size_t position) {
  out << std::string(position, ' ') << "(" << v.x << ", " << v.y << ", " << v.z
      << ")\n";
}

void draw(const Polygon3D &p, Screen &out, size_t position) {
  out << std::string(position, ' ') << "<polygon>" << std::endl;
  for (auto v : p.vs)
    ::draw(v, out, position + 2);
  out << std::string(position, ' ') << "</polygon>" << std::endl;
}

class Drawable {
  struct IDrawable {
    virtual ~IDrawable() = default;
    virtual std::unique_ptr<IDrawable> copy_() const = 0;
    virtual void draw_(Screen &, size_t) const = 0;
  };

  template <typename T> struct DrawableObject final : IDrawable {
    T data_;
    DrawableObject(T x) : data_(std::move(x)) {}
    std::unique_ptr<IDrawable> copy_() const override {
      return std::make_unique<DrawableObject>(*this);
    }
    void draw_(Screen &out, size_t position) const override;
  };

  std::unique_ptr<IDrawable> self_;

public:
  template <typename T>
  Drawable(T x) : self_(std::make_unique<DrawableObject<T>>(std::move(x))) {}

  // copy ctor, move ctor and assignment
public:
  Drawable(const Drawable &x) : self_(x.self_->copy_()) {}
  Drawable(Drawable &&x) noexcept = default;
  Drawable &operator=(Drawable x) noexcept {
    self_ = std::move(x.self_);
    return *this;
  }

public:
  friend void draw(const Drawable &x, Screen &out, size_t position) {
    x.self_->draw_(out, position);
  }
};

using Model = std::vector<Drawable>;

void draw(const Model &x, Screen &out, size_t position) {
  out << std::string(position, ' ') << "<world>" << std::endl;
  for (const auto &e : x)
    draw(e, out, position + 2);
  out << std::string(position, ' ') << "</world>" << std::endl;
}

template <typename T>
void Drawable::DrawableObject<T>::draw_(Screen &out, size_t position) const {
  ::draw(data_, out, position);
}

int main() {
  Model document;
  document.push_back(0);
  document.push_back(Polygon3D{{2, 1, 6}, {-3, 7, 4}});
  document.push_back(document);
  document.push_back(Vector3D{-3, 7, 4});
  draw(document, std::cout, 0);
}
```
Тут условное описание хода мыслей того, как необходимо думать о проектировании данного кода и данной архитектурной задачи:

So our first intention - we want to pass a container to draw.

Then we understand, that best is always a vector, leave comment if choose from the rest, and we take it, but problem is that it's homogeneous container, so we need some technique to be able to store heterogeneous types in homogeneous container. In simple words we need a kind of a wrapper for it.

Since we figure out what we want to draw, thus that wrapper should be able to erase type of initial data first and provide somehow generic capabilities for draw call for every possible type that we want to store inside wrapper. So we will call draw indirectly.

And here we have all in place.
Drawable - is literally a wrapper, it does the job by delegating it to the inner templated interface IDrawable, which describe our real intent - copy_ and draw_ witch are generated from template for every possible type we store. copy_ here is just take own a pointer to wrapper, so it could be defined once, but draw_ is a trickier one, since here we delegate it to a free function, since it's not our concern as a Drawable how to do this since it operations involves several classes, we only care that we can do it somehow.

So we have runtime polymorphism when we call functions depending on stored type of object, and we have static polymorphism when we generate code for inner Interface class and implementations of draw delegation for possible stored classes.   

And quote for understanding, since Drawable is a value type.

В этом тут сила этой семантики, так как иначе прокидывание документа внутрь документа вызывало бы бесконечную рекусию, а тут у нас нормально копируется объект, который не зависим от изначального.

A **value type** is like a “self-contained box” where copying, assignment, moving, and destruction behave predictably and independently, regardless of the operations you can perform on the content.

**Принцип подстановки Лисков:**
Более общие классы должны быть более общими и по составу и по поведению:
```cpp
class Polygon3D : public Polygon2D {};
```
Это читается как: трёхмерный полигон может быть использован во всех контекстах, где может быть использован двумерный полигон. Если данное утверждение некорректно (как в примере сверху), то наследоваться попросту нельзя.

Предусловия алгоритмов также не могут быть усилены производным классом.
Постусловия алгоритмов не могут быть ослаблены производным классом.
Ещё раз - заменимы ВО ВСЕХ контекстах.

Важной для `LSP` является концепция ковариантности.
### Ковариантность к генерализации
Мы говорим, что изменение типа ковариантно к генерализации, если выполняется условие:
"если `A` обобщает `B`, то `A`' обобщает `B`'"

Собственно, указатели ковариантны к генерализации,
если трактовать `A'` = `A*`:
```cpp
class Rectangle : public Shape {/*....*/}

void draw(Shape *shapes, size_t size);

Rectangle rects[5];
draw(rects, 5); // ok since Rectangle* is a Shape*
```
### Инвариантность
Поведение выше ощущается как что-то само собой разумеещееся, но это не так:
```cpp
class Rectangle : public Shape {/*....*/}

void draw(std::vector<Shape> shapes);

std::vector<Rectangles> rects(5);
draw(rects); 
// fail since vector<Rectangle> is not a vector<Shape>
```
Т.е. в общем-то шаблоны являются **инвариантными к генерализации**.
"если `A` обобщает `B`, то между `A'` и `B'` нет вообще никаких отношений".
### Обсуждение: всё ли так просто?
Можно поставить обратный вопрос: а почему, собственно, указатели не инвариантны к генерализации?
```cpp
template <typename T> using Pointer = T*;
// казалось бы

void draw (Pointer<Shape> shapes, size_t size);

Pointer<Rectangle> rects = new Rectangle[5];
draw(rects, 5); 
// ok

// но чем Pointer<Rectangle> лучше чем 
// std::vector<Rectangle> ??
```
Оказывается, **ковариантными являются только одинарные указатели**.
Таким образом, ковариантность указателей и ссылок к обобщению это приятное исключение для `LSP`, а не общее правило.
### Контрвариантность
Мы говорим, что изменение типа **контрвариантно к генерализации**, если 
выполняется условие:
"если `A` обобщает `B`, то `B'` обобщает `A'`"

Контрвариантны, например, возвращаемые значения методов.
### Обсуждение
Именно ковариантность указателей и ссылок и их не подверженность срезке делают их отличными кандидатами в `C++` для реализации `LSP`.
Но к сожалению, как мы видели ранее, их использование приводит к появлению неявных (`incidental`) структурам данных и убивает тем самым `value`-семантику.
