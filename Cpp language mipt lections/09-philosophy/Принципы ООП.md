## Базовые понятия
- Контекст инкапсулирует данные и охраняет инварианты.
- Контекст реализует интерфейс (для типов в C++ через наследование интерфейса)
- Производный контекст расширяет базовый (для типов в C++ через наследование реализации)
- Если контексты это типы, производный контекст связан с базовым дополнительными соотношениями (частное/общее, быть частью и подобными)
- Если несколько типов реализуют общий интерфейс, вызовы их методов через этот интерфейс полиморфны.

## Обсуждение: проектирование
Проектирование - это моделирование отношений между типами.
Примеры отношений: "A наследует от B" или "C является полем в B"

## Обсуждение
UML это средство описания, которым можно описать систему абсолютно любую, в том числе, сколь угодно плохую.

Software имеет анлийский корень soft, означающий нечто, что легко изменять. Но очень часто у нас вместо куска пластелина в руках некая засохшая субстанция с гвоздями.

Первый шаг к хорошему коду - это **легко изменяемый** код.
Собственно, отсюда вытекает, что характеристикой плохого кода является трудность в его расширении, эволюции.

Люди много думали и придумали ряд принципов для написания этого хорошего кода, ну или по крайней мере хорошо расширяемого кода.

# Принципы SOLID
1. **SRP** - single responsibility principle
   *Каждый контекст должен иметь только одну ответственность*
2. **OCP** - open-close principle
   *Каждый контекст должен быть закрыт для изменения и открыт для расширения*
3. **LSP** - Liskov substitution principle
   *Частный класс должен свободно замещать общий во всех контекстах, который подразумевает связь между ними.*
4. **ISP** - interface separation principle
   *Тип не должен зависеть от тех интефейсов, которые он не использует*
5. **DIP** - dependency inversion principle
   *Высокоуровневые классы не должны зависеть от низкоуровневых*

### Guideline: связность
Ваши сущности должны быть внутренне связаны(cohesive) и внешне разделены.

Разделяй всё, что может быть разделено, без создания жёстких внешних связей. Пример - отделение контейнеров от алгоритмов.

"Cohesion is a measure of strength of association of the elements inside a module. A highly cohesive module is a collection of statements and data items that should be treated as a whole because they are so closely related."
(Tom DeMarco)

Он же, Шон, выделяет такие вот проблемные, как в нашем примере,
incidental data structures, где мы имеем структуру в одном месте, а потом мы в другом классе агрегируем такие структуры в контейнер и хотим дальше с ними что-то делать. Беда в том, что эти две инцидентные (да, как рёбра в графе) структуры не связаны между собой напрямую, например, наследники или композиционно связаны (одно поле в другом) они связаны неочевидно, через контейнер, который хранит один из них, на самом деле храня то, с чем сам толком не знает, как работать. Отсюда мы и пришли ранее к тому, что Vector3D должен сам знать о том, что он должен будет делать в Screen - классе, о структуре и роли которого он знать не знает и не должен. Собственно справедлио и обратное, а они таки связаны в итоге..

Тезис Шона состоит в том, что одна из целей проектирование - избегать появления таких структур в вашем проекте. Но как?...

К слову, у него есть и другие утверждения:
- no raw loops
  (иначе говоря либо функция состоит буквально из одного цикла, либо в ней нет циклов)
- no synchronization primitives


Рассмотрим ситуацию с идеальным контейнером и идеальным классом внутри контейнера - int. Value-семантика сохранена, мы можем туда сложить любые объекты типа int и всё будет работать для них одинаково.
```cpp
using document_t = std::vector<int>;

// документ хранит объекты
// семантика значения на месте
// no incidental data structures 

document.push_back(1);
document.push_back(2);
document.push_back(3);

draw(document, std::cout);
```
Т.е. мы хотим что-то такое:
```cpp
using document_t = std::vector<???>;

// документ хранит объекты
// семантика значения на месте
// no incidental data structures 

document.push_back(circle);
document.push_back(polygon);
document.push_back(vector);

draw(document, std::cout);
```
На самом деле, в идеальной ситуации, мы бы хотели хранить и полиморфно отображать **разнородные** объекты.
