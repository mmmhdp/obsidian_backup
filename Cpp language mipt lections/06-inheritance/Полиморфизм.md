# Общий интерфейс
Мы можем спроектировать классы Triangle() и Polygon() так, чтобы у
них был общий метод square(), вычисляющий площадь.

Можем ли мы тогда сохранить массив из объектов некого, неважно какого, типа, единственной важной характеристикой которого будет наличие у объектов данного типа метода square()?

Ответ - конечно можем. Для этого мы должны сделать для них общий 
интерфейс и отнаследоваться от него.
```cpp
struct ISquare {
	void square ();
// главный вопрос - а как реализовать данный метод?
};

struct Triangle: ISquare {};
// реализует свой метод square()  

struct Poligon: ISquare  {}; 
// реализует свой метод square()  

std::vector <ISquare*> v; 
/*
 хранит и Polygon* и Triangle*
*/
```
## Попытка реализации 1: указатель на метод
```cpp
class ISquare {
	sometype *sqptr_;
public:
	ISquare(sometype *sqptr): sqptr_(sqptr) {}
	double square() {
		sqptr_->square();
	}
};


template <typename T>
struct Triangle: public ISquare {
	Point <T> x, y, z;
	Triangle () : ISquare(this) {}
	double square() const;
};
```
Проблемы:
- Ранее уже обсуждалось, что для вызова метода класса необходим объект класса (this необходим), т.е. sometype на самом деле это 
  некая хитрая городушка с набором указателей.

Благо, написания данного кода не является необходимым, так как за нас данную функциональность с поддержанием таблиц функций для вызова и 
разрешением того, что и когда вызывать по указателю реализует механизм 
**виртуальных функций**, который в общих чертах и выглядит так, как описанный выше код.
# Попытка 2: Языковая поддержка: virtual
```cpp
struct ISquare 
{
	virtual double square () const;
	/*
	 не полностью виртуальная функция в интерфейсе,
	 т.е. вообще можно создать объект данного 
	 класса, что бессмысленно абсолютно,
	 должно быть:
	virtual double square () const = 0;
	
	 у данного класса нет виртуального диструктора,
	 посыпется без этого очищения резурсов у классов-
	 наследников, должно быть:
	virtual ~ISquare () = default;
	*/
};


template <typename T>
struct Triangle : public ISquare {
	Point <T> x, y, z;
	double square () const;
	/*
		а тут не указан модификатор override, 
		отсутствие которого может вызвать ошибки,
		так как базовый square() не будет определён 
		как базовый, что и вызовет ошибки.	
	*/
};

/*
	но есть и ещё проблема - возвращаемым типом, 
	который вообще говоря не подходит всем T, 
	т.е. данный класс-интерфейс вообще говоря хорошо бы 
	сделать шаблонным
*/ 

template <typename T>
struct ISquare 
{
	virtual T square () const;
};

template <typename T>
struct Triangle : public ISquare<T> {
	Point <T> x, y, z;
	T square () const override;
};
```
Это всё ещё **очень плохой код**, но он показывает концепцию.
# Таблица виртуальных функций
При создании класса хотя бы с одним виртуальным методом в него добавляется vptr.

Конструктор базового класса динамичеки выделяет память для таблицы виртуальных функций.

Конструктор каждого потомка производит инициализацию данной таблицы своими методами, т.е. в итоге в данной таблице всегда окажутся нужные нам указатели.

# Порядок конструирования
При наследовании он имеет ключевое значение.

Сначала необходимо инициализировать объект базового класса, который невидимо для наших глаз сконструирует таблицу виртуальных функций.

А уже после конструктор подобъекта заполнит эту таблицу своими методами:
```cpp
template <typename T> struct Triangle : ISquare {
	Point <T> x, y, z;
	double square () const;
	Triangle() : ISquare(), x{}, y{}, z{} {}
};
```

Важно - таблица виртуальных функций считается полностью заполненной только после окончания конструктора, т.е. формально после:
```cpp
	Triangle() : ISquare(), x{}, y{}, z{} {
	} // <- вот тут, после скобочки
```
# Статический и динамический тип
Рассмотрим функцию:
```cpp
double sum_square (const ISquare &lhs, const ISquare &rhs) 
{
	return lhs.square() + rhs.square();
}

Triangle t; Poligon p;
sum_square (t, p);
```
**Статическим типом** для lhs и rhs является известный на этапе компиляции тип const ISquare&.

При этом в конкретном вызове функции у них могут быть разные **динамические типы**.
![[Pasted image 20251209120826.png]]

Т.е. когда мы говорим о шаблонах - это статический полиморфизм, там известны все типы на этапе компиляции.

А когда мы говорим о полиморфизме виртуальных функций - это динамический полиморфизм, типы разрешаются на этапе исполненния.

# Проблемы с overloading
Здесь допущена человеческая ошибка с типами int и long
```cpp
struct Matrix {
	virtual void pow (int x);
};
struct SparceMatrix : Matrix{
	void pow (long x); 
};


Matrix *m = new SparceMatrix;
m->pow(3); 
/*
	увы, но вызовется Matrix::pow,
	а не SparceMatrix::pow,
	так как для override необходимо 
	полное совпадение по аргументам, 
	иначе она буквально не попадает в таблицу 
	виртуальных функций.
	
	если указать override на SparceMatix::pow,
	компилятор буквально скажет, что непонятно,
	что я пытаюсь переписать, так как он не может
	найти виртуальную функцию для референса, что как
	бы раскрутка в обратную сторону. 
	
	т.е. SparceMatrix не overrided, а overloaded в данном 
	контексте.
*/ 
```
# Overload vs override
Начало тут [[Полиморфизм#Overriding и Overloading]]

**Переопределение функции** (overriding) это замещение в классе наследнике виртуальной функции на функцию наследника.

**Перегрузка функции** (overload) это введение того же имени с другими типами аргументов.

Аннотация override сообщает, что мы конкретно имели ввиду в данном случае. И может быть применена только к виртуальной функции, но при этом писать перед ней virtual не нужно - компилятор это и так знает.
```cpp
struct Matrix {
	virtual void pow (int x);
};
struct SparceMatrix {
	virtual void pow (int x) override;
	// тут virtual - масло масленное 
	void pow (int x) override;
	// такой записи достаточно
};
```
# Pure virtual method
Наличие хотя бы одного такого в классе отбирает возможность создать объект данного класса. 
```cpp
struct A {
  virtual void pow(int x) const = 0;
};

A a; // compilation error
```
# Virtual destructor
Виртуальный деструктор предназначен для того, чтобы уничтожать объекты производного класса по указателю на базовый класс.
```cpp
struct ISquare {
	virtual double square () const = 0;
	virtual ~ISquare(){};
};
```

# Интерфейсные классы
Класс, в котором все методы чисто виртуальные служит своего рода общим интерфейсом
```cpp
struct ISquare {
	virtual double square () const = 0;
	virtual ~ISquare(){};
};
```
Такой класс называется абстрактным базовым классом.

К сожалению, виртуальный конструктор (в том числе и копирующий конструктор) не возможен в таком классе.

Тогда становится неясно, а как тогда скопировать по базовому классу
Выход есть.
# Виртуальное копирование
Обычно используется виртуальный метод clone
```cpp
struct ISquare {
	// всё остальное
	virtual ISquare* clone () const = 0;
};

template <typename T> class Triangle : public ISquare {
	std::array<Point <T>, 3>  pts_;
	Triangle* clone() const override {
		return new Triangle{pts_};
	}
	/*
		использование именно в качестве возвращаемого
		типа, а не в агрументах (они ковариантны),
		Triangle* тут не является ошибкой,
		так как из-за публичного наследования 
		Triangle* is-a *ISquare, иначе это можно 
		сформулировать так, что Triangle и ISquare
		контрвариантные типы.  
	*/
};
```
# Срезка возвращается
Из-за невозможности виртуальных конструкторов, срезка возможна при передаче по значению:
```cpp
void foo (A a)
{
	std::cout << a << std::endl;
}

B b1 (10);
foo(b1); 
/*
 на экране "5", как будто для A,
 говорят, что произошла срезка (slice) класса B
 до класса А
*/
```
**Поэтому никогда не передавайте объекты базового класса по значению**.

Используйте для этого указатель или ссылку:
```cpp
void foo (A &a)
{
	std::cout << a << std::endl;
}

B b1 (10);
foo(b1); //  на экране "5 10", как для B
```

# Языковая поддержка: final
С учётом вышеописанных историй, возникает вопрос, а нам теперь всегда 
писать virtual destructor, от нас же могут отнаследоваться?

Когда будут - тогда надо, а вот если мы хотим убрать оверхед на vtable и запретить наследование, то выход есть.

final - это модификатор класса, говорящий о том, что от данного класса нельзя наследоваться. Наследование от такого класса будет ошибкой компиляции.
```cpp
class Foo final {};
```


# Пишем классы правильно: 4 способа
Класс в C++ написан правильно, если выполнено хотя бы одно из четырёх условий:
1. Класс содержит виртуальный деструктор
2. Класс объявлен как final
3. Класс является stateless и подвержен EBCO [[EBCO]] (возникает при создании mixin классов - состоят только из функций, а ещё так можно реализовать систему тегов с пустыми классами в роли тегов)

   Тут не пишут виртуальный деструктор, так как он это самое EBCO ломает, а тогда и толку от идеи нет.
4. Класс не может быть уничтожен извне, но может быть уничтожен потомком (protected destructor)

Первые два - железобетонные, остальные - игра с огнём

# Языковая поддержка: protected
Модификатор protected служит для защиты от всех, кроме наследнков 

Он позволяет писать чисто-базовые классы:
```cpp
class PureBase {
// anything
protected: 
	~PureBase () {}
};
```

Тогда объект класса наследника просто нельзя удалить по указателю на базовый класс и проблема снимается.

Если не удалять изнутри класса тогда всё по прежнему.

А ещё помогает девиртуализации (режет косвенность).
# Виртуальные функции и их эффекты
Добавляет оверхед, так как добавляет степени косвенности на вызовы методов. Особенно мрачно становится при множественном наследовании.

Ну и открывает множество новых способов ошибиться.
# PVC
PVC (pure virtual call) - вызов чисто виртуального метода.
```cpp
struct Base
{
	virtual void doIt () = 0;
	Base () { doIt(); } // PVC invocation
};
struct Derived : Base
{
	void doIt() override
};

int main(){
	Derived d; // PVC appears
}
```

Вызов чисто виртуальной функции является ошибкой не только в конструкторе или деструкторе, но и вообще внутри любой функции,
которая внутри них вызывается.

В конструкторе таблицы ещё нет, а в десрукторе уже нет.
Важно - любой вызов из них таким образом не является виртуальным, 
а значит даже override не поможет разрешить PVC, таблицы то нет, 
чтобы оно работало.

Вывод - не вызывать никогда функции внутри конструктора и деструктора, 
кроме случая final классов.

А вызов в другой может привести к такому вот скрытому PVC, 
по косвенности не сможет компилятор доказать, что там PVC, поэтому 
тут стрельнет в рантайме:
```cpp
struct A {
  A() { doIt_driver(); }

  void doIt_driver() { doIt(); };

  virtual void doIt() = 0;
  virtual ~A() = 0;
};

struct B : public A {
  void doIt() override {}
};

int main() { B b; }
```

# Статическое и динамическое связывание
Говорят, что виртуальные функции **связываются динамически** (так называется процесс разрешения адреса через vtable во время исполнения (late binding)) 

Обычные функции **связываются статически**.
Даже если физически они приходят из динамических библиотек или являются позиционно независимыми и адресуются через PLT, это неважно.

**На уровне модели языка** они считаются связывающимися статически.

Увы, но многи другие вещи имеют статическое связывание, например аргументы по умолчанию.

## Связывание аргументов по умолчанию
Как уже было сказано, они связываются статически, т.е. **зависят только от статического типа**.
```cpp
#include <iostream>

struct Base {
  virtual int foo(int x = 52) { return x; };
};

struct Derived : public Base {
  int foo(int x = 13) override { return x * 2; };
};


int main() {
Base *pb = new Derived{};
std::cout << pb->foo() << std::endl;
/*
А на экране 104, а не 26...
Хотя вызвана будет именно Derived::foo,
но дело в том, что она будет связана динамически,
а аргумент по умолчанию свяжется статически в Base
классе.
*/

Derived *pd = static_cast<Derived *>(pb);

std::cout << pd->foo() << std::endl;
/*
А вот если привести к Derived*, то будет таки 26
*/
}
```
Вывод - **не надо использовать аргументы по умолчанию с вируальными функциями!**

Но выход есть - идиома [[NVI]]

# Два полиморфизма
Полиморфной (по данному аргументу) называется функция, которая ведёт себя по разному в зависимости от **типа** аргумента.

**Полиморфизм** бывает **статический**, когда функция управляется известными на этапе компиляции типами и **динамический**, когда тип известен только на этапе выполнения.

Примеры:
- Множество перегрузки можно рассматривать как одну статически полиморфную функцию (по любому аргументу)
- Шаблон функции - это статически полиморфная функция (по любому аргументу)
- Виртуальная функция - это динамически полиморфная функция (по первому неявному аргументу this)
## Но насколько их можно мешать?
- Может ли существовать шаблон виртуального метода?
  Нет, дело в том, что для такой реализации vptr из одномерной таблицы будет переходить в n-мерную, в зависимости от того, сколько теперь в таком случае агрументов будут определять динамический полиморфизм.
  
  А это страшный оверхед для решения на уровне языка, но решения данной задачи существуют (Multiple Dispatch problem), **Andrei Alexandrescu** в своей книге _Modern C++ Design_ предлагает решение данной задачи, эмулируя на уровне фреймворка с помощью станадартных средств языка данное поведение.

- Можно ли перегружать виртуальные функции?
  К сожалению, можно, манглирования имён позволяет это сделать, но это вызывает крайне мрачные последствия из-за скрытия имён.
### Перегрузка виртуальных функций
Предположим, что мы умеем эффективно возводить разреженные матрицы в целые степени и хотим просто переиспользовать его для возведения в дробные:
```cpp
struct Matrix {
	virtual void pow (double x); // обычный алгоритм
	virtual void pow (int x); // эффективный алгоритм
};

struct SparseMatrix : public Matrix {
	void pow (int x) override;
	// крайне эффективный алгоритм
};

SparseMatrix sm;

sm.pow(1.5)
/*
	А вызовется не Matrix::pow(double), 
	а SparseMatrix::(int)...
	
	Дело в том, что имена для формирования множества
	перегрузки будут взяты из SparseMatrix::, 
	а там только один кандидат, который и параметр один
	имеет и implicit cast из double в int существует, 
	короче выйграет он.
	
	А дальше компилятор не пойдёт, так как логика такая,
	раз перегрузил тут, значит далее не надо искать.
	
	Заметим, что если бы тут кандидатов не было вообще, 
	тогда бы компилятор заглянул на огонёк к Matrix::, 
	где бы нашёл то, что нам нужно, но он туда просто не
	пойдёт. 
*/
```
Но как бороться с этим? Мы же хотим вызвать именно перегруженную виртуальную из класса родителя. Из обозначенного выше можно предположить, что нам необходимо как-то втащить пространство имён класса родителя в данном случае, в класс наследник.

А ровно для этого, для втаскивания имён из одного namespace в другое и используется using:
```cpp
struct Matrix {
	virtual void pow (double x); // обычный алгоритм
	virtual void pow (int x); // эффективный алгоритм
};

struct SparseMatrix : public Matrix {
	using Matrix::pow;
	// втаскиваем все pow'ы
	
	void pow (int x) override;
	// крайне эффективный алгоритм
};

SparseMatrix sm;

sm.pow(1.5)
/*
 с обновлённым множеством перегрузки, вызовётся то, что 
 мы и ожидаем, т.е. Matrix::pow(double)
*/
```
