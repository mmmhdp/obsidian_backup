Для реализации идеи "`B является A`" (также назывется отношением "`is-a`") можно попробовать пользоваться уродливыми конструкциями, которые слабо расширяемы и ещё хуже читаемы.

Поскольку данная идея лежит в основе построения любой условно математической модели того или иного процесса, что и заметил создатель  языка `C++` Бьёрне Страуструп, хорошо было бы иметь данную конструкцию как часть самого языка. Такая конструкция в языке `C++` называется наследованием.

Открытая форма наследования синтаксически записывается так:
```cpp
class A {};

class B : A {} // B IS ALSO A
```
![[Pasted image 20251205133509.png]]

А далее мы можем считать, что класс-родитель - это всего лишь поле в нашем классе, что например, позволяет делегировать часть конструирования  класса конструктору класса родителя:
```cpp
struct Node {
	Node *parent_;
	Node_t type_;
};

struct BinOp : public Node {
	BinOp op_;
	Node *lhs_ = nullptr, *rhs_ = nullptr;	
	
	BinOp (Node *parent, BinOp_t opcode) :
		Node {parent, Node_t::BINOP}, op_(opcode) {}
	/*
		Вот тут и вызовется в списке инициализации 
		конструктор класса родителя
	*/
	
};
```
Всех наследников, как следует из диаграммы, объединяет отношение "`is-a`", т.е. объект производного класса одновременно является и объектом базового класса, что ведет к тому, что указатели и ссылки на эти классы приводятся друг к другу неявным приведением.

А обратно можно привести с помощью `static_cast`:
```cpp
struct Node;
struct BinOp: public Node;

void foo(const Node& pn);

BinOp *b = new BinOp(p, op);

foo(*b); // ok
Node *pn = b; // ok
b = static_cast<BinOp*> (pn); // ok
```
# Смыслы открытого наследования и вытекающие проблемы
У открытого наследования на самом деле есть два смысла, которые не связаны между собой:
- B **расширяет** A
- B **является частным случаем** A 

Проблема часто называется проблемой "квадрата и прямоугльника" или  "круга и эллипса".

И вот тут дело в том, что с одной стороны, в квадрате одно поле для  стороны, а в прямоугольнике их два, т.е. как-будто бы логично взять сначала квадрат, а потом отнаследовать от него прямоугольник, добавив ещё поле длины, тогда получится, что ПРЯМОУГОЛЬНК РАСШИРИТ КВАДРАТ. 
```cpp
struct Square {
	double x; // x * x square
	void double_square(Square& s){
		s.x *= sqrt (2.0);
	}
};


struct Rectangle: public Square {
	double y; // x * y rectangle
};


Rectangle r {2, 3};

r.double_square();
// и что тогда это такое будет?
```

НО, с другой стороны, на самом деле именно квадрат является ЧАСТНЫМ СЛУЧАЕМ ПРЯМОУГОЛЬНИКА, т.е. как бы удобно наследовать квадрат от прямоугольника.
```cpp
struct Rectangle{
	double x, y; // x * y rectangle
	void double_square(Rectangle& r){
		r.x *= sqrt (2.0);
	}
};

struct Square : public Rectangle {
// Тут лишнее поле y
};
	
Square r {2};

r.double_square();
/*
	и что тогда это такое будет? стало ещё хуже, 
	теперь у квадрата не равны стороны...
*/
```
Т.е. в данной ситуации, две грани, два смысла публичного наследования нас заводят в перпендикулярные друг другу направления.

Решение состоит в том, что оба данных подхода не верны, эти два класса не связаны отношениями ребёнок - родитель, тут что то другое.

Как возможный вариант, оба данных класса на самом деле удобно было бы отнаследовать от некого класса `Shape`, с виртуальным методом `double_square`, который каждый из них перегрузил в своём стиле. А ещё лучше не стороны было бы хранить, а координаты вершин, что упрощает наследование от данных фигур в дальнейшем.

Итог - если отношения между классами не удовлетворяют **сразу двум**  **обозначенным критериям публичного наследования** - значит просто не надо наследоваться, надо думать над перепроектированием. 

Данный принцип известен как принцип подстановки Лисков и является одним из принципов `SOLID`.
## Принцип подстановки Лисков
Типы `Base` и `Derived` связаны отношениями `is-a` (`Derived` является `Base`), если любой истинный предикат (вернее любой интересующий нас истинный предикат, т.е. утверждение о свойстве объекта) относительно  `Base` остаётся истинным при подстановке `Derived`.

Именно данный принцип даёт возможность завести в языке неявное приведение из `Derived` в `Base`.

Для `C++` этот принцип выполняется с точностью до декодирования.

При правильном проектировании всегда есть возможность подставить
`Derived*` вместо `Base*` или `Derived&` вместо `Base&`.

Подстановка значений в `C++` сопряжена с некоторыми проблемами.
### Проблема срезки (первое приближение)
```cpp
struct A {
	int a_;
	A(int a) : a_(a) {}
};
struct B: public A {
	int b_;
	B(int b) : A(b / 2), b_(b) {}
};

B b1(10);
B b2(8);

A& a_ref = b2;
a_ref = b1; // b2 == ??
/*
	Тут значения в b2 разойдутся, так как в данном случае
	во время копирования скопируются только те поля, 
	которые относятся к типу A.
	Т.е. для b2 теперь ситуация:
	b2.a_ = 5, но при этом b2.b_ = 8 (старое значение, до 
	копирования присвоенное)
*/
```

Базовая срезка возникает из-за того, что присваивание не полиморфно:
```cpp
struct A {
	int a_;
	A(int a) : a_(a) {}
	/*
	Из того, что нагенерировал компилятор:
	
	A& operator= (const A& rhs) {
		a_ = rhs.a_;
	}
	*/
};


a_ref = b1; a_ref.operator=(b1); b1 приводится к const A&
```

Было бы здорово, если бы функция во время исполнения вела себя по 
разному, в зависимости от реального, настоящего типа своих аргументов...

Конечно, к присваиванию это не относится, тут это скажем ожидаемая семантика, тут скорее пример для мотивации подобных функций.
### Полиморфное поведение
**Полиморфная функция** - эта такая функция, которая ведёт себя по разному, в зависимости от типов и количества аргументов, которые ей были переданы. 

Например, любое множество перегрузки - это полиморфная функция, как и любая шаблонная функция.

Далее туда [[Полиморфизм]].
# Контроль доступа и разновидности наследования
К текущему моменту нам известны такие модификаторы доступа как:
- `public` - доступно всем
- `protected` - доступно только потомкам 
- `private` - доступно только самому себе

Также знаем, что `public` наследование вводит отношение `is-a` между классами [[Наследование#Смыслы открытого наследования и вытекающие проблемы]].

Рассмотрим иные варианты соотношений.
## Разновидности наследования
Рассмотрим, как изменяется модификатор полей в зависимости от типа наследования:

||public inheritance|protected inheritance|private inheritance|
|-|-|-|-|
|public becomes|public|protected|private|
|protected becomes|protected|protected|private|
|private becomes|non reachable|non reachable|non reachable|

Т.е. приватные поля вообще не доступны в наследнике вне зависимости от типа наследования.

Также заметим, что в свою очередь приватное наследование эквивалентно композиции в закрытой части, иначе говорят, что оно моделирует соотношение `part-of`.

Неявного приведения типов при этом не происходит, т.е. `static_cast` для закрытого наследования работать перестаёт, что логично.
### Отношение `part-of`
Рассмотрим подходы к симуляции данного соотношения между классами.

**Закрытое наследование**:
```cpp
class Whole : Part {
	// everything else
};
```

**Композиция**:
```cpp
class Whole {
	// everything else
private:
	Part p_;
};
```

Ключевое отличие наследования:
- Возможность переопределять виртуальные функции из базового класса
- Доступ к защищённым (`protected`) полям базового класса
- Возможность использования `using` и вводить имена базового класса в область видимости класса наследника

Композиция должна быть выбором по умолчанию.
