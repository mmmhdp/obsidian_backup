# Case study: MyArray
Допустим у вас есть интерфейс IBuffer, использованный в Array
```cpp
class Array {
 protected: 
	 IBuffer *buf_; 
 public: 
	 explicit Array(IBuffer *buf) : buf_(buf) {}
	// something interesting
};
```

Вы реализовали ваш собственный превосходный класс MyBuffer, наследующий от IBuffer.

Как теперь написать класс MyArray, наследующий от Array и использующий MyBuffer?
# Первая попытка: двойное включение
Мы можем попробовать сохранить MyBuffer внутри:
```cpp
class MyArray : public Array {
protected:
	MyBuffer mbuf_;
public:
	MyArray (int size) : 
	mbuf_(size), Array(&mbuf_) 
	// order problems are here, Array have to be first
	{}
	// smth MORE interesing
};
```
Проблема в том, что это работать не будет, так как буфер нельзя инициализировать раньше базового класса, базовый класс обязян инициализироваться первым.

С другой стороны, переставить местами инициализаторы мы тоже не можем, так как буфера ещё не будет создано, т.е. аргумент для инициализации базового класса ещё не будет существовать к моменту инициализации.

Но будь Array всего лишь полем, всё бы заработало, мы можем влиять на порядок инициализации полей, но вот беда, мы хотим оставить is-a отношение. Тогда, отбросив невероятное, оставляем "невозможное" - уравниваем эти объекты в правах инициализации, добавив MyBuffer в список классов, от которых мы наследуемся.

# Множественное наследование
```cpp
class MyArray : protected MyBuffer, public Array {
public:
	explicit MyArray(int size) : MyBuffer(size),Array(???){}
	// more stuff
};
```

Синтаксис наследования - все базовые классы с модификаторами через запятую

Здесь наследование защищенное, так как:
- Мы не хотим прятать защищённую часть MyBuffer и не можем сделать его приватным
- Мы не хотим показывать MyBuffer наружу и не можем сделать его публичным

Остаётся один вопрос, а что же тогда в итоге писать вместо знаков вопроса?

Решение - если бы в MyBuffer уже было бы что-то, чем можно инициализировать Array, то тогда было бы идеально, мы бы это и передали в конструктор Array. 

Чтобы это "что-то" появилось, воспользуемся proxy классом.
## Proxy class
```cpp
struct ProxyBuf {
	MyBuffer buf;
	explicit ProxyBuf(int size) : buf(size) {}
};

class MyArray : protected ProxyBuf, public Array {
public:
	explicit MyArray(int size) : 
	ProxyBuf(size), Array(&ProxyBuf::buf){}
	// more stuff
};
```
Теперь всё срастается. 

Но послевкусие оставляет желать лучшего, выглядит всё это как костыль или черная магия.

Оказывается, она во многих языках запрещена. Её нет в Java, нет в C#, а эти языки во многом именно что объектно ориентированы. Причина состоит во множестве нетривиальных проблем, которые может вызвать наличие подобного функционала. Собственно, одну из таких мы сейчас решали.

Стоп проблемой для введения во многих языках стал вопрос - а что если у нас есть поле в классе, одно и тоже, но наследуемое по разным путям?
Далее ответ на данный вопрос мы обсудим, в C++ ведь такого рода наследование не запрещено на уровне языка.

Возвращаясь к нашим баранам, в данном случае проблема не с идеей множественно наследования как такового, а проблема в том, что мы пытаемся реализовать множественное наследование от реализаций, а не от интерфейсов, именно эта идея является сомнительной.

Наследование интерфейсов таких вопросов не вызывает, как и сказано ранее:
```cpp
class Man : public ITwoLegs, public INoFeather {
public:
	// методы двуногих
	
public:
	// методы для лишённых перьев
	
// прочее
};
```

А не вызывает оно вопросов потому, что наследование интерфейсов оставляет наследованию только один смысл из двух. Вместо публичного наследования как генерализации (is-a) и наследования как расширения (добавление полей) или закрытого наследования (part-of) и опять же расширения, остаётся только is-a или part-of, так как интерфейсные классы (или их ещё называют абстрактными) попросту не имеют состояния, нет там никаких полей, т.е. там нечего расширять. 

В таком свете публичное наследование лишь говорит нам о том, что объект связан отношением генерализации (is-a или part-of, это не важно) с рядом сущностей, он и то, и это, и прочее. Например, человек и двуногое, и без перьев, и пяти палое и т.д. и т.п.

# Наследование реализации
Выше мы уже обсудили нетривиальность наличия в языке множественно наследования реализации, а сейчас мы обсудим то, как выглядит разрешение заданных ранее вопросов.
## Ромбовидные схемы
Рассмотрим следующий пример:
```cpp
struct File { int a; };
struct InputFile : public File { int b; };
struct OutputFile : public File { int c; };
struct IOFile : public InputFile, public OutputFile {
 int d;
};
```

И тут возникает вопрос, вот поле a от кого наследуется, доступно ли оно нам вообще? А IOFile получается теперь два раза File?
### Проблемы ромбовидных схем
Поскольку в объект нижнего класса входят два верхних подобъекта, доступ к переменным неочевиден.
```cpp
IOFile f {11};
int x = f.a; // ошибка!

int y = f.InputFile::a; 
/*
 ок, тут мы помогли и указали нужного наследника,
 но постоянно так делать - это боль, тем более это 
 спокойно может привести к потере инвариантов
*/
```

Более того, в процессе реализации, f.InputFile::a и f.OutputFile::a могут разойтись в процессе работы.

В качестве решения хотелось бы иметь один экземпляр базового класса, сколькими бы путями он не пришёл в производный класс.

Такие базовые классы называются **виртуальными**.

# Виртуальные базовые классы
Виртуальное наследование поддержано в языке:
```cpp
struct File { 
	int a;
	virtual ~File() {}
};
struct InputFile : virtual public File { int b; };
struct OutputFile : virtual public File { int c; };
struct IOFile :
/*
	тут virtual уже не нужно вставлять,
	virtual - это аннотация для базового класса
*/
 public InputFile, public OutputFile {
 int d;
};

IOFile f {11};
int x = f.a; // теперь ок
int y = f.InputFile::a; 
// тоже работает и более того эти вещи эквивалентны
```

Само собой, тут возникает масса вопросов.
## Немного вопросов и ответов
- Что если базовый класс виртуальный не по всем путям?
  С виртуальных путей в итоге будет получен один объект базового класса, плюс ещё по одному объекту с каждого невиртуального пути.
- Что если базовый класс виртуальный но в нижнем подобъекте он всего один?
	Будет всё также работать, как при обычном наследовании, только хуже, ведь при разрешение множественного наследования степень косвенности вызовов в итоге может повысится даже в этом случае. 
- В каком порядке и когда конструируются обычные и виртуальные подобъекты?
	Сначала все виртуальные, потом все обычные.
## О таблице виртуальных функций для множественного наследования.
Вызов виртуальной функции при множественном наследовании должен пройти через дополнительный уровень диспетчеризации.

А при виртуальном наследовании через **ещё один дополнительный уровень** из-за того, что таблицы для виртуальных подобъектов должны быть отдельно смержены.

## Списки инициализации
Виртуальный базовый класс **обязан появиться** в списке инициализации самого нижнего подобъекта:
```cpp
struct InputFile : virtual public File {
	InputFile() : File(smth1) /*, other staff*/
	// File(smth1) не вызовется для IOFile
};

struct OutputFile : virtual public File {
	OutputFile() : File(smth2) /*, other staff*/
	// File(smth2) не вызовется для IOFile
};

struct IOFile : public InputFile, public OutputFile {
	IOFile() : File(smth3), InputFile(), OutputFile()
	/*, other staff*/ {}
};

IOFile f; // вызовет File(smth3)
```
