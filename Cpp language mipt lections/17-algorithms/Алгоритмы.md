# Функторы и состояние
## Обсуждение: `for each`
У нас есть метод `equal_range` в `unordered_multimap`, который возвращает диапазон пар ключ-значение с одинаковым ключом.
```cpp
std::unordered_multimap<int, int> m;
....
auto [begin, end] = m.equal_range(i);
```
Вы можете как-то проитерироваться и что-то сделать с каждым значением:
```cpp
for (auto it = begin; it != end; ++it) f(*it); // 1
std::for_each(begin, end, f); // 2
```
Какой из двух вариантов вы выберете и почему?
## Обсуждение
Выбирать всегда следует алгоритм стандартной библиотеки.
- Аргумент от тела цикла:
```cpp
for (auto elt : cont) {
	// позволяет неконтролируемо добавить сюда 
	// массу кода, скорее всего лишнего
}
```
- Аргумент от распараллеливания(`С++17`):
```cpp
for_each(
	std::execution::par, cont.begin(), cont.end(), func
);
```

В общем случае абстракция циклов повышает и читаемость и эффективность кода. Такого рода абстракции называются **абстракциями с отрицательной стоимостью**.
## Обсуждение
Представим, что нам надо как-то использовать внешнее значение.
Например, пусть нам надо умножить `value` на некоторое число:
```cpp
int mult = get_my_mult(); // очень долгая функция
for (auto it = begin; it != end; ++it)
	it->second *= mult;
```

Кажется, что тут нет способа сделать вызов `std::for_each`?
```cpp
int mult = get_my_mult(); // очень долгая функция
std::for_each(std::execution::par, begin, end,
	[](auto &&elt){elt.second *= mult}; // ошибка
) 
```
## Идея функтора
Допустим, мы написали класс с состоянием и оператором вызова:
```cpp
struct Multer {
	int m;
	Multer (int mult) : m(mult) {}
	void operator () (auto &&elt) {elt.second *= m;}
};
```
Тогда становится возможным следующее:
```cpp
int mult = get_my_mult(); // очень долгая функция
std::for_each(std::execution::par, begin, end, 
	Multer{mult});) 
```
Но на каждый чих не наздравствуешься.
Неудобно каждый раз писать функтор.
Делать это нам помогают возможности захвата переменных в лямбдах.
## Hello, lambda world
Давайте посмотрим на лямбды в блеске и славе:
```cpp
int main(int argc, const char **argv) {
	return [argv] () -> int {
		std::cout << "Hello from:" << argv[0] << std::endl;
		return 0;
	} ();
}
```
Мы можем это упростить, выкинув пустое тело и выводимый тип:
```cpp
int main(int argc, const char **argv) {
	return [argv] {
		std::cout << "Hello from:" << argv[0] << std::endl;
		return 0;
	};
}
```
Или так:
```cpp
hi = [argv] () {
	std::cout << "Hello from:" << argv[0] << std::endl;
	return 0;
};

hi();
```
## Обсуждение
Лямбда-выражения - это не функции:
```cpp
auto t = [k = z] (auto x, auto y) { return x < y  * k ;};
```
Это скорее классы с перегруженным `operator()`:
```cpp
struct __closure_type_for_t {
	int __k;
	auto operator() (auto x, auto y) const {
		return x < y * __k;	
	}
};

__closure_type_for_t t{z};
```
## Убираем `const`
Если мы хотим изменять захваченный по значению контекст мы должны сделать нашу лямбду в явном виде `mutable`:
```cpp
auto t = [z](auto x, auto y) mutable {
	z += 1; return x < y * z;
};
```
Обратите внимание, что `z` меняется в пределах замыкания:
```cpp
auto s = t;
t(1, 2); // z изменилось внутри t, но не внутри s;
```
Замыкания по умолчанию копируемые (если не захвачено ничего со стёртым `copy ctor`).
Глобальные и статические переменные захватывать не нужно, они доступны и так.
## Виды захвата
Захват по значению (по ссылке):
```cpp
auto fval = [a, b](int x) {return a + b * x;};
auto fvalm = [a, b](int x) mutable { a += b * x; return a;};
auto fref = [&a, &b](int x) { a += b * x; return a;};
```
Захват по ссылке всегда `mutable` и отслеживает состояние переменной:
```cpp
a = 42;
fval(x); // тот же
fref(x); // использует новое a
```
Разумеется, можно смешивать:
```cpp
[&a, b, &c, d] { a += c * b; c+=d; return a+c};
```
Захват всего контекста по значению(по ссылке):
```cpp
auto faval = [=](int x) {return a + b * x;};
auto fаref = [&](int x) { a += b * x; return a;};
```
Захват всего по значению и частично по ссылке и наобарот:
```cpp
auto favalb = [=, &b](int x) {return a + b * x;};
auto fаrefa = [&, a](int x) { b += a * x; return b;};
```
Захват с переименованием:
```cpp
auto freval = [la = a](int x) {return la + x;};
auto freref = [&la = a](int x) { la += x; return la;};
```
Захват с переименованием позволяет захватить правую ссылку:
```cpp
std::ostream_iterator<int> os {std::cout, " "};
std::vector v = {1, 2, 3};

auto out = [w = std::move(v), os] {
	std::copy(w.begin(), w.end(), os);
};
```
Теперь вектор передан в состояние замыкания.
Передача осуществляется в контсрукторе замыкания, т.е. в момент создания функции, а не в момент её вызова.
Т.е. список захвата выполнится именно в месте создания объекта замыкания, а не в месте вызова.

## Захват в теле класса
```cpp
struct Foo {
	int x;
	void func (){
		[x] mutable { x+= 3; } (); // FAIL
		[&x] { x+= 3; } (); // FAIL
		
		[=] { x+= 3; } (); // OK, but depricated in C++20
		[&] { x+= 3; } (); // OK, the right way to catch
		
		[this] { x+= 3; } (); // OK
	}
};
```
Это всё работает потому, что захват всего захватывает и `this`.
## Локальный контекст
```cpp
auto factory (int parameter){
	static int a = 0;
	return [=](int argument){
		static int b = 0;
		a += parameter;
		b += argument;
		return a + b;	
	};
}

auto func1 = factory(1);
auto func2 = factory(2);

cout << func1(20) << " " << func1(30) << " "
	 << func2(20) << " " << func2(30) << std::endl;
```
Определение класса замыкания - одно, т.е. `a` и `b` будут общими.
`a` как для фунции `factory`, а `b` как статическая переменная для перегруженного `operator()` внутри замыкания.

## Единая типизация замыканий
```cpp
auto t = [&x, &y] {return x + y;}
```
Тут не вполне ясно, а что такое `auto`...
Мало того, так нельзя делать в теле класса:
```cpp
struct Foo {
	auto t = [&x, &y] {return x + y;} // ошибка
};
```
Мы понимаем, что это `closure type`, но не можем записать его явно.
В этом случае, мы можем частично стереть тип:
```cpp
auto t = [&x, &y] {return x + y;} 
// closure

std::function<int()> f = [&x, &y] {return x + y;} 
// function
```
`std::function<сигнатура>`- это единный тип, к которому **приводятся** все замыкания с данной сигнатурой.
Ключевое слово тут "приводятся":
```cpp
t = [] {return 52;} // FAIL
f = [] {return 52;} // OK
```
Тип функции теряет информацию о захвате контекста.
Значение имеет только сигнатура.

## Снова захват в теле класса
```cpp
using VVTy = std::function<void(void)> 
// void arg here is not mandatory

struct Foo {
	int x;
	
	VVTy xplus1 = [&] { x += 3}; // OK, but hmmm...
	VVTy xplus2 = [this] { x += 3}; // OK
};
```
Это вдвойне интересно, так как такие лямбды-члены ведут себя как методы.
```cpp
struct Foo f {10};

f.xplus1(); // OK, x = 13
```
## Информация о конкретном типе
Механизм `std::function` унифицирует типы замыканий.
Информация о реальном типе возвращается через `target_type`:
```cpp
int f(int);

function<int(int)> fn1 = f,
					fn2 = [](int a) {return -a;},
					fn3 = [x](int a) {return x-a;};
cout << fn1.target_type().name() << endl
	 << fn1.target_type().name() << endl
	 << fn1.target_type().name() << endl
	 << fn1.target_type().name() << endl;
```
## Case study: finally
Допустим у нас очень простой класс:
```cpp
struct Finally {
	std::function<void()> action_;
	explicit Finally(std::function<void()> action) :
		action_(std::move(action)) {}
	~Finally () { action_();}
};
```

Теперь мы можем вот такие фокусы:
```cpp
FILE *f = fopen("myfile.dat", "r"); 
assert(f);

Finally close_f([&f]{ fclose(f); });
```
## Обсуждение: `heap indirection`
Есть некоторая проблема с таким подходом к `finally`, а именно производительность. Гораздо эффективней иметь `closure`:
```cpp
template <typename ActTy>
inline auto Finally(ActTy fn) {
	struct Finally_impl {
		ActTy act_;
		explicit Finally_impl(ActTy action) :
			act_(std::move(action)) {}
		~Finally_impl() {act_();}
	};
	
	return Finally_impl(std::move(fn)); // bingo
}
```
Функция необходима для вывода типов.
А можно ли сделать `deduction hint`?

Можно, но не нужно, `CTAD (class template argument deduction)` решает этот вопрос без нашей помощи.

## Предостережение
У вас могут возникнуть соблазн сделать функтор с изменяемым состоянием:
```cpp
auto [begin, end] = m.equal_range(i);

int max = 0;
std:for_each(begin, end, [&max](auto&& elt){
	int n = f(elt.second);
	if (n > max) max = n;
});

std::cout << "Answer is: " << max << std::endl;
```
Это не будет ошибкой, но это дурной тон.
Функтор с состоянием - иногда нужно, но почти всегда некрасиво.

Объяснить можно так - это функцие-подобный объект, наличие захвата - это не осоновная характеристика объекта, и даже более, скорее не самая необходимая. Отсюда и такие утверждения.

# Алгоритмы
## Алгоритмы
Алгоритм стандартной библиотеки - это **функция**, выполняющая действие над **интервалами**, заданными с помощью итераторов.
```cpp
template <typename InputIt, typename OutputIt>
OutputIt copy(InputIt fst, InputIt last, OutputIt res);
```

Имя алгоритма также может иметь суффиксы и префиксы:
- `if`(например `copy_if`) - выполнить действие при выполнении предиката
- `n`(например `copy_n`) - выполнить действие ограниченное кол-во раз
- `copy`(например `reverse_copy` - разместить результат в новом контейнере
- `stable`(например `stable_partition`) - алгоритм работает стабильно

Вопрос, должен ли в языке сущесвовать `copy_n` - дискуссионный.
## Несколько примеров `copy_x`
```cpp
int arr[] = {2, 3, 5, 7, 11, 13, 17};

std::vector<int> v(7);

std::copy_n(arr, 7, v.begin());

std::copy(v.begin(), v.end(),
	std::ostream_iterator<int>(std::cout, "\n"));
// на экране: 2 3 5 7 11 13 17

std::fill(v.begin(), v.end(), 0);

std::copy_if(arr, arr + 7, v.begin(),
	[](int i){
		return (i % 3) == 1;
	}
)

std::copy(v.begin(), v.end(),
	std::ostream_iterator<int>(std::cout, "\n"));
// на экране: 7 13 0 0 0 0 0
```
## Обсуждение: специализации циклов
Есть довольно серьёзное заблуждение, что все алгоритмы это `for_each`.
Общее правило: более специализированный алгоритм лучше менее специализированного.

Алгоритм в этом смысле можно рассматривать как **специализацию цикла**:
- Обычный `for` это что угодно, компилятор и библиотека ничего не знают и соптимизируют как угодно.
- Но тот же `copy` это именно копирование и ничто иное.

Важнейший навык - выбирать правильные алгоритмы.
Для этого необходимо видеть **паттерны в коде**.
## Паттерны в коде: `find_if`
Классический паттерн: `for`, внутри `if`, внутри `break`:
```cpp
for (auto&& elt : v)
	if (check(elt)) {
		action(elt);
		break;
	}
```
Разумеется, это `std::find_if`
```cpp
auto it = std::find_if(v.begin(), v.end(),
	[](auto&& elt){ return check(elt);}	
);

if (it != v.end())
	action(*it);
```
## Иногда и `find_if` много
Допустим, вам принесли код, который использует `find_if`:
```cpp
if (std::find_if(v.begin(), v.end(), p) != v.end())
	action();
```
Его можно и даже нужно упростить далее:
```cpp
if (std::any_of(v.begin(), v.end(), p)) // есть ли элемент?
	action();
```

Аналогично для `std::all_of` и `std::none_of`.
Мы всегда должны стремиться к выбору самого специализированного алгоритма из существующих.
## Обсуждение: и это частая проблема
На самом деле это частая ситуация.
Если вы видите, как кто-то пишет:
```cpp
auto [ita, itb] = 
	std::mismatch(a.begin(), a.end(), b.begin());
	
if (ita != a.end() && itb != b.end())
	action();
```
То такому человеку надо вежливо объяснить, что он просто забыл про то, что существует более специализированный способ:
```cpp
if (!std::equal(a.begin(), a.end(), b.begin()))
	action();
```

## Паттерны в коде: `transform`
То, что в функциональных языках называется `map`, в `C++` это `transform`
```cpp
std::vector<int> v = {2, 3, 5, 7, 11, 13};
```
Неправильно: `for_each` тут пытается что-то сделать над текущим элементом:
```cpp
std::for_each(v.begin(), v.end(), [](auto& i){i = -i;});
```
Обратите внимание: при использовании правильного алгоритма легко заменить входной итератор:
```cpp
auto negate = [](auto&& i) {return -i;};
std::transform(v.begin(), v.end(), v.begin(), negate);
```
![[Pasted image 20260113173515.png]]
Идея такая - `for_each` подразумевает, что мы используем каждый элемент, но не меняем его самого, а вот если мы хотим отработать по каждому элементу и обновить его новым значением (т.е. модифицировать последовательность) - тоже `transform` является тем самым, более узким алгоритмом.
## Обсуждение: функция как предикат
Предположим, хочется использовать функцию `std::toupper`.
Как написать алгоритм её вызова с предикатом?
```cpp
std::string s = "hello";

// увы, это не будет работать
std::transform(s.begin(), s.end(), s.begin(), std::toupper);
```
А причина банальная `std::toupper` это множество перегрузки.
Компилятор не понимает, какую из перегруженных функций взять.

Как вы выкрутитесь?
Ответ:
```cpp
#include <algorithm>
#include <cctype>
#include <iostream>

char foo(char c) { return std::tolower(c); }

int main() {
  std::string s = "hello";

  // увы, это не будет работать
  // std::transform(s.begin(), s.end(), s.begin(), std::toupper);

  std::transform(s.begin(), s.end(), s.begin(), ::toupper);
  // плохой C-style вариант, но перегрузки нет 
  // для С кода - а значит от работает
  std::cout << std::endl << s << std::endl;

  std::transform(s.begin(), s.end(), s.begin(), foo);
  // уже лушче, но стоит ли это создания foo? 
  std::cout << std::endl << s << std::endl;

  std::transform(s.begin(), s.end(), s.begin(),
    [](char c){return std::toupper(c);});
  // конечно нет, а вот для лямбды в самый раз
  std::cout << std::endl << s << std::endl;
}
```
## Второй смысл `transform`
У этого алгоритма есть форма, где он работает как своего рода `zip`:

Дополнительно к нему `std::transform_reduce` позволяет аккумулировать бинарную операцию над ними.

Интересно, что тоже самое делает `std::inner_product`, но делает это **иначе**. Он не паралелит, а делает честно одно за другим.

Т.е. в итоге получаем, что `std::transform_reduce` требует ассоциативную операцию (`(a op b) op c = a op (b op c)`) на `reduce` - иначе UB, а вот `std::inner_product` справится без проблем.
## Отличия в гарантиях
Есть такие пары фунций, которые существуют с разными гарантиями на исполнение.

Например, `reduce` и `accumulate`:
- Обе берут бинарную операцию и считают результат, но
- `accumulate` гарантированно делает это за `in-order`
- `reduce` же сделает это как угодно

Ещё пример - `inclusive_scan` и `partial_sum`.
Также - `transform_reduce` и `inner_product`

Мы должны внимательно читать документацию и осозновать такие вещи.

if (std::all_of(v.begin(), v.end(), p)) // true

## Паттерны в коде: `remove`
Как бы вы написали функцию `remove`?
Идея функции: удалить из диапазона все значения `val`:
```cpp
template <typename Iter, typename T>
Iter remove(Iter fst, Iter lst, const T& val) {
	// а что тут?
}
```
Правильный ответ: **никак**.
По итератору нечто можно удалить из контейнера только используя:
```cpp
Cont.erase(it);
```

Правильная мысль - а давайте мы не будем удалять - давайте лучше мы сместим нужное в одну сторону, а ненужное - в другую. 
Тогда вернув итератор на начало и конец нужной части (или только на конец - чтобы мы самостоятельно явно удалили "хвост") мы и получим новый диапазон, без "удалённых" элементов. Этот паттерн так часто возникает, что для него выделена целая идиома.
## Идиома `erase-remove`
Как по настоящему работает `remove`?
```cpp
std::vector<int> v = {
	1, 42, 2, 42, 3, 42, 4
};

auto result = std::remove (v.begin(), v.end(), 42);
v.erase(result, v.end());
```
Или, группируя это в одну фразу:
```cpp
v.erase(std::remove(v.begin(), v.end(), 42), v.end());
```
Эта техника и называется `идиома erase-remove`.
![[Pasted image 20260114100650.png]]
## Обсуждение: `erase-xxx` - не только `remove`
Среди алгоритмов не только `remove` удаляет элементы.
Например, `unique`:
```cpp
vector v = {1, 1, 2, 2, 3, 3, 4};

std::sort(v.begin(), v.end());
v.erase(std::unique(v.begin(), v.end()), v.end());
```
Это по факту та же форма, что и `erase-remove`, только без `remove`.
К счастью, пока что в стандарте `C++` три (а сейчас их там также?) таких алгоритма:
1. `remove`
2. `remove_if`
3. `unique`

Но в пользовательском коде, может, понятное дело, быть всякое. 
Более того, люди и правда часто пишут `remove`- подобные функции ровно для использования в обобщённой идиоме `erase-xxx`.

## Сортировки и недосортировки
Задача: получить `первые N по величине` элементов контейнера `cont` всё равно в каком порядке. После этого вывести их на экран.
1. `sort(cont.begin(), cont.end());`
2. `partial_sort(cont.begin(), cont.begin() + N, cont.end());`
3. `nth_element(cont.begin(), cont.begin() + N, cont.end());`

Все три алгоритма решают задачу.
Но понятно, что третий вариант требует для этого меньше времени.

## Обсуждение
У нас есть заведомо сортированные контейнеры, такие как `std::set` и есть возможность создать сортированный диапазон на последовательном контейнере.

## Бинарный поиск
Неявное ограничение всего семейства таких алгоритмов: 
они работают только на сортированных интервалах
```cpp
vector<int> v = {
	81, 9, 54, 36, 27, 63, 18, 72, 45
};

sort(v.begin(), v.end());

if (binary_search(v.begin(), v.end(), 37)){
	// сюда мы не попадём, так ведь?
	
	// да, если v отсортирован
	// UB - если нет
}
```
Надо добавить: мы туда **в лучшем случае** не попадём.
## Поисковые алгоритмы
- `binary_search` - есть элемент или нет его
- `lower_bound` - где мог бы быть элемент, если бы он был (слева)
- `upper_bound` - где мог бы быть элемент, если бы он был (справа)
- `equal_range` - есть ли элемент и если да, то где

Сложность каждого из них логарифмическая.
