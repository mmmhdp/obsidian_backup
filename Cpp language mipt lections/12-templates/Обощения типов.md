# Инстанцирование
Инстанциирование - это процесс порождения специализации:
```cpp
template <typename T>
T max(T x, T y) {return x > y ? x : y;}

//...

int m = max<int>(3, 4);
// порождает template<> int max (int x, int y)
```
Мы называет этот процесс неявным (`implicit`) инстанциированием.
Оно порождает код через подстановку параметра в шаблон.
## Инстанцирование и специализация
Явная специализация может войти в конфликт с инстанцированием:
```cpp
template <typename T> T max(T x, T y){
//....
};

// ok, указываем явную специализацию
template <> double max (double x, double y) {return 52.0;}

// никакой implicit istantiation не нужно
int foo() {return max<double>(2.0, 3.0);}
// и вернёт он 52.0, следуя нашей заданной руками 
// специализации

// процесс implicit istantiation нужно и он произошёл
int foo() {return max<int>(2, 3);}

// ошибка: ODR violation
template <> int max (int x, int y) {return 52;}

/*
	Делая специализацую, мы делаем её как бы за компилятор.
	В данном примере компилятор к моменту появления
	нашей специализации уже сгенерировал такую же, 
	поэтому мы получаем ошибку переопределения.
*/
```
## Удаление специализаций
Частным случаем явной специализации является удаление специализации:
```cpp
// для всех указателей
template <typename T> void foo(T*);

// но не для char* и не для void*
template <> void foo<char>(char *) = delele;
template <> void foo<void>(void *) = delele;
```

Подобным образом можно удалять и перегрузки:
```cpp
 void foo(char *) = delele;
 void foo(void *) = delele;
```

## Инстанцирование - ленивый процесс
Ниже если бы инстанцирование было энергичным, была бы ошибка:
```cpp
template <int N> struct Danger {
	using block = char[N]; // ошибка, если N < 0
};

template <typename T, int N> struct Tricky {
	void test_lazyness() {Danger <N> no_boom_yet;}
};

int main () {
	Tricky <int, -2> t; // ok
	// ошибка только если будет вызвано
	// t.test_lazyness();
}
```
Но в данном случае инстанцировалось ровно то, что мы попросили и ошибки нет.
## Явное инстанцирование
Неявное инстанцирование компилятор проводит где захочет.
Но вы можете взять точку инстанцирования под контроль:
```cpp
template <typename T>
T max (T x, T y) {return x > y ? x : y;}

template int max<int>(int x, int y); // инстанцировать тут
```
Вы можете (и часто должны) также заблокировать инстанцирование в остальных модулях, указав, что оно уже проведено где-то ещё.
```cpp
extern template double max<double>(double x, double y);
```
При явном инстанцировании, очевидно, вы лишаетесь ленивого поведения

## Специализаци по `nontype` параметрам
Нет никаких проблем в том, чтобы специализировать класс по любой разновидности шаблонных параметров.

Например, таким параметром могут стать целые числа:
```cpp
template <typename T, int N> class Array;

template <typename T> class Array<T, 3> {
// тут более эффективная реализация 
// для массива из трёх элементов
}
```
Немного сложнее придумать разумный пример специализации по указателям и ссылкам. 
## Специализация для похожих типов
Частичная специализация возможна по семейству похожих типов:
```cpp
template <typename T> struct X;
template <typename T> struct X<std::vector<T>>;

X<int> a; // -> primary template X<T>
X<std::vector<int>> b; // -> X<std::vector<T>>
```

Примерно также можно специализировать для всех функций:  
```cpp
template <typename R, typename T> struct Y;
template <typename R, typename T> struct Y<R(T)>;
```
## Упрощение имён в специализациях
Внутри основного шаблона класса мы всегда можем сокращать имена:
```cpp
template <class T> class A {
	A* a1; // A здесь означает A<T>
};
```

Это отлично работает внутри частичной специализации:
```cpp
template <class T> class A<T*> {
	A* a2; // A здесь означает A<T*>
};
```
Разумеется, указывать полные имена вполне легально (и часто куда лучше читается).
## Case study: `unique_ptr`
Рассмотрим следующее использование `unique_ptr`:
```cpp
std::unique_ptr<int> ui {new int[1000] ()}; 
// грубая ошибка
// в деструкторе просто delete вместо delete[]
```
Хорошая ли идея добавить специализацую вида:
```cpp
std::unique_ptr<int[]> ui {new int[1000] ()};
// хотелось бы как-то так
```
Но хороша ли идея добавлять данную специализацию именно в класс `unique_ptr`?

В общем мы можем это сделать, так как специализации добавлять в пространство имён `std::` можно, туда нельзя добавлять перегрузки функций.

Проблема такого подхода в другом. Дело в том, что если мы решим добавить данную специализацую для класса, мы будем также вынуждены написать реализации всех методов класса. Но частичной специализации именно методов не существует... Метод - это нечто очень близкое к функции, а частичная специализация возможна только для того, что являтся классом (структурой). Тогда есть ещё идея - мы ранее уже прокидывали класс для очистки ресурсов, так может тогда и шаблон будет ожидать что-то подобное?
### Вспоминаем структуру `unique_ptr`
Удаление в неё отделено в параметр шаблона:
```cpp
#include <memory>
template <typename T, 
typename Deleter = std::default_delete<T>>
class unique_ptr {
  T *ptr_;
  Deleter del_;

public:
  unique_ptr(T *ptr = nullptr, Deleter del = Deleter())
      : ptr_(ptr), del_(del) {}

  ~unique_ptr() { del_(ptr_); }

  // и т.д.
};
```
### Частичная специализация: `default_delete`
На самом деле, мы хотели бы частично специализировать тот самый `Deleter`, а не класс.

И тогда нам приходит на помощь частичная специализация для массивов для этого класса:
```cpp
template <typename T> struct default_delete {
	void operator(T* ptr) {
		delete ptr;
	}
};

template <typename T> struct default_delete <T[]> {
	void operator(T* ptr) {
		delete [] ptr;
	}
};
```
Вот теперь подставновка произойдёт верно и при массиво-подобном `T` и у нас будет вызван правильный `deleter`. И тогда будет работать то, что мы рассматривали раньше как желаемое:
```cpp
std::unique_ptr<int[]> ui {new int[1000] ()};
```
## Напрушение `LSP` для шаблонов
Увы, но (частично) специализированный шаблон может не иметь
ничего общего с его полной версией (вплоть до  разных имён методов).

С точки зрения наследования, это нарушение `LSP`:
```cpp
template <typename T> struct S { void foo(); };
template <> struct S<int> { void bar(); };

S<double> sd; 
sd.foo(); // primary template S<T>
sd.bar(); // error!

S<int> si; si.bar(); // specialization S<int>
si.foo(); // error!
```

И разумеется, повторим, что шаблоны инвариантны к шаблонной генерализации [[Принципы ООП#LSP]]. Каждая специализация считается новым, не связанным с прочими, типом.
## Обсуждение
В продолжении темы, рассмотрим вызов `si.bar()` внутри шаблонной функции:
```cpp
template <typename T> 
int foo(T si) { return si.bar();}
```
Учитывая ленивость подстановки и возможность потенциального нахождения специализации, когда компилятор должен принять решение о валидности данного вызова? Ответ на данный вопрос требует погружения в тему разрешения имён.
# Разрешение имён
## Постановка проблемы
Должно ли разрешение имён в шаблонах (в том числе классов) происходить до инстанцирования или после?
```cpp
template <typename T> struct Foo {
	int use () {return illegal_name;}
};
```
Здесь `illegal_name` выглядит нелегальным именем, но может быть оно будет как-то легализовано после того, как будет подставлен конкретный `T`?

Нужно ли сразу сообщить об ошибке или подождать подстановки параметра?
## Двухфазное разрешение имён
**Первая фаза**: до инстанцирования
Шаблоны проходят общую синтаксическую проверку, а также разрешаются **независимые** (от параметра) имена.

**Вторая фаза**: во время инстанцирования
Происходит специальная синтаксическая проверка и разрешаются **зависимые** имена.

**Разрешение имени** - имя связывается с той сущностью, которую оно именует.

Зависимое имя (упрощённая формулировка, см. стандарт) - это имя, которое семантически зависит от шаблонного параметра. Шаблонный параметр может быть его типом, он может участвовать в формировании типа и так далее:
```cpp
template <typename T> struct Foo {
	int use () {return illegal_name;}
	// будет ошибка, так как illegal_name 
	// не зависит от параметра но является не легальной
	// конструкцией - ошибка на первой фазе 
	// разрешения имён 
};
```
Другой пример:
```cpp
template <typename T> struct Foo {
	int use () {return T::illegal_name;}
	// решение об ошибке будет принято 
	// во второй фазе разрешения имён	
};
```

**Золотое правило**:
`Разрешение зависимых имён откладывается до подставновки шаблонного параметра.`
## Пример Вандерворда
Можно ли исправить ситуацию?
```cpp
template <typename T> struct Base {
	void exit();
};

template <typename T> struct Derived : public Base<T> {
	void foo () {
		exit();
// и вот тут можно подумать, что это Base::exit(),
// но на самом деле exit - не зависимое имя, так что нет, 
// решения опять будет принято на первой фазе.

// а смешно то, что до второй фазы уже всё решится и 
// данное имя свяжется с функцией из стандартной библиотеки...
	}
};
```

Решение проблемы раз:
```cpp
template <typename T> struct Base {
	void exit();
};

template <typename T> struct Derived : public Base<T> {
	void foo () {
		Base::exit();
		// читается как Base<T>::exit();
	}
};
```

Решение проблемы два:
```cpp
template <typename T> struct Base {
	void exit();
};

template <typename T> struct Derived : public Base<T> {
	using Base<T>::exit;
	void foo () {
		exit();
	}
};
```

Решение проблемы три:
```cpp
template <typename T> struct Base {
	void exit();
};

template <typename T> struct Derived : public Base<T> {
	void foo () {
		this->exit();
		// ага, мы стреляем именно что в двухфазное разрешение, откладывая разрешение до второй фазы
	}
};
```
Данная техника вызова через явный `this` - эта та причина, по которой вызывать в классе что-то через `this` - плохая идея, читающий будет думать о данном паттерне с разрещение имён!
## Зависимые имена типов
Зависимые имена типов могут вызывать неожиданные проблемы:
```cpp
struct S {
	struct subtype {};
};

template <typename T> int foo(const T &x) {
	T::subtype *y;
	// и т.д.
}

foo<S>(S{}); // казалось бы, всё хорошо?
```
А теперь готовьтесь:
```cpp
T::subtype  *  y;
// * в данном контексте - это умножить...
// упадёт с ошибкой о том, что y - неизвестное имя.........
```
Тут компилятор не понимает, что `subtype` - это именно тип, а не поле.
У него правило - всё, что похоже на поле - это именно что поле.

Для того, чтобы это заработало, надо помочь старому:
```cpp
struct S {
	struct subtype {};
};

template <typename T> int foo(const T &x) {
	typename T::subtype *y;
	// теперь y - это указатель на тип T::subtype
	// и т.д.
}

foo<S>(S{}); // А теперь всё действительно хорошо
```
Эта техника называется устранением неоднозначности (`disambiguation`).
## Зависимые имена шаблонов
Зависимые имена шаблонов также могут вызывать неожиданные проблемы:
```cpp
template <typename T> struct S {
	template <typename U> void foo();
};

template <typename T>  
void bar () {
	S<T> s;
	s.foo<T>();
}
// всё ок или нет?))
```
Ловим ядро:
```cpp
s.foo < T>();
// s.foo меньше T............, а дальше синтаксическая ошибка 
```
Опять старый ошибся и думает, что `foo` - это что-то вроде поля в `s`, разрешение-то отложено до второй фазы. Опять надо помогать...
```cpp
template <typename T> struct S {
	template <typename U> void foo();
};

template <typename T>  
void bar () {
	S<T> s;
	s.template foo<T>();
}
// Вот теперь всё работает как надо
```
И воспоминание с первой лекции тогда обретают смысл:
```cpp
typename T::template iterator<int>::value_type v;
/*
typename говорит о том, что вот всё это 
дальше является именно типом - 
T::template iterator<int>::value_type

Но нельзя указать просто 
typename T::iterator<int>::value_type v;
тут уже не ясно, а что такое T::iterator и он будет считан как поле, а не как зависимый тип шаблона, поэтому эта часть тоже является необходимой для полного разрешения данного имени. 
*/ 
```
# Вывод типов
## Обсуждение
Вернёмся к примеру с функцией `max`:
```cpp
template <typename T>
T max(T x, T y) {return x > y ? x : y;}

// ....

a = max<int>(2, 3);
// порождает template <> int max(int, int)
```

Компилятор видит тип `int` для литералов, поэтому его явное указание не нужно:
```cpp
a = max(2, 3); // тоже ок

a = max(2, 3.9);
// не ок, возникает неоднозначность, вывод типов не сработает

a = max<int>(2, 3.9);// тоже ок, т.к. мы тут помогли компилятору и получили template int max(int, int), а дальше уже аргументы implicit приведением, как при обычном вызове функции у нас почти всегда и происходит, будут оба аргумента приведены к int. 
```
Важное замечание - при выводе типов компилятор никогда не лезет через `implicit cast`, тип должен чётко совпасть, потом только произойдёт его подстановка.
## Неуточнённые типы
По исторической традиции, вывод неуточнённого типа режет ссылки, константность и прочее:
```cpp
template <typename T>
T max(T x, T y) {return x > y ? x : y;}

const int &b = 1, &c = 2;

a = max(b, c); // ->template<> int max(int, int)
```
С точки зрения семантики `int &`, `const int &`, `const int` - это всё что-то в роде `int`, понятно, что с точки зрения реализации `int &` ближе к указателю, но тут предпочтение отдаётся семантике.

Это сделано, чтобы уменьшить число неоднозначностей:
```cpp
int e = 2; int &d = e; // вроде разные типы, но вывод работает

a = max(d, e); // ->template<> int max(int, int)
```
Тут срезание и вывод такого рода не считаются даже за `implicit_cast`, так как тут это происходит всегда.
## Уточнённые типы
Всё меняется, когда мы уточняем тип левой ссылкой или указателем:
```cpp
template <typename T> void foo(T& x);
```
Теперь компилятор резонно считает, что программисту виднее:
```cpp
const int x = 52;
foo(x); // -> template void foo<const int>(const int& x)
```
Интересно, что иногда мы вроде уточнили, а компилятор... срезал это точнение:
```cpp
template <typename T> void bar(const T x);

const int x = 52;
bar(x); // -> template void bar<int>(int)
```
Но тут это логично, просто `const arg` - это по сути ничего не имеющая смысла конструкция, собственно, слегка отходя от темы, перегружать по ней тоже нельзя, поэтому тут опять же отдаётся предпочтение в сторону семантики при выводе типов.

Особая статья - это уточнение правой ссылкой, это мы пока отложим.
## Вывод конструкторами класса (`C++17`)
Начиная с `C++17` конструкторы классов могут использоваться для вывода типов:
```cpp
template<typename T> struct container{
	container(T t);
	// и т.д.
};

container c(52); // -> container<int> c(7);
```
Внезапно, будет работать также и списочная инициализация, но пока не ясно, как это она так:
```cpp
std::vector v {1,2,3}; // ->std::vector<int>
```
## Проблема: вывод через косвенность
Конструктор класса сам может быть шаблонным:
```cpp
template<typename T> struct container {
	template<typename Iter> container(Iter beg, Iter end)	;
	// more code
};

std::vector<double> v;
container d (v.begin(), v.end()); // ->container<double>???
```
Компилятор умён, но не настолько умён, чтобы сходить в `std::iterator_traits`, тут ему необходимо подсказать, где конкретно искать `value_type`. Делается это с помощью `deduction hints`.
### Подсказки для вывода(`Deduction hints`) `C++17`
Пользователь может помочь выводу в сложных случаях:
```cpp
template<typename T> struct container {
template<typename Iter>container(Iter beg, Iter end);
	// more code
};

// пользовательский хинт для вывода
template<typename Iter>
struct container (Iter b, Iter e) ->
	container<typename iterator_traits<Iter>::value_type>;
	
std::vector<double> v;
container d (v.begin(), v.end()); // ->container<double>
```
Пояснение:
```cpp
template<typename Iter>
struct container (Iter b, Iter e) ->
	container<typename iterator_traits<Iter>::value_type>;
/*
это значит, что когда кто-то вызовет данный конструктор
	struct container (Iter b, Iter e), 
создай объект класса с типом после стрелочки, т.е. 
	container<typename iterator_traits<Iter>::value_type>;
*/
```
## Вывод без конструктора(или с дефолтным конструктором)
Агрегатное значение может и не иметь конструктора:
```cpp
template<typename T> struct NameValue {
	T value;
	std::string name;
};
```
Тоже можно немного помочь компилятору:
```cpp
NamedValue(const char*, const char*)->
	NamedValue<std::string>;
```
А теперь конструируем агрегат из двух строк:
```cpp
NamedValue n{"hello", "world"}; // NamedValue<std::string>
```
## `auto` и `decltype`
Шаблоны выводят типы и это хорошо.

А что по локальным переменным? Может быть и они могут также? И да, могут.

Для локальных переменных ключевое слово `auto` работает `по правилам вывода типов шаблонами`:
```cpp
template<typename T> foo(T x);

const int &t = 52;

foo(t); // -> foo<int>(int x)

auto s = t // -> int s;
```
Для точного вывода типа в том виде, с которым переменная была введена, без срезок, которые мы обсуждали выше, существует ключевое слово `decltype`:
```cpp
decltype(t) u = 1; // -> const int &u
```
Как мы знаем, если в скобки можно что-то передать, туда что-то обязательно улетает интересное, так и тут.
```cpp
decltype(t + 1) u = 1; // -> ???
```

### Четыре формы `decltype`
`decltype` существует в двух основных видах:
1. Для имени
2. Для выражения

`decltype(name)` выводит тип, с которым было объявлено имя.
`decltype(expression)` работает сложнее:
- `decltype(lvalue)` это тип выражения + левая ссылка
- `decltype(xvalue)` это тип выражения + правая ссылка 
- `decltype(prvalue)` это тип выражения 

В итоге, левые и правые сслыки встречаются в неожиданных местах:
```cpp
int a[10];

decltype(a[0]) b = a[0]; // -> int &b
```
Это может выглядеть странновато, но на самом деле это логично - ссылка определяет `lvalueness`.
Т.е. главной характеристикой выражения `a[0]` в данном контексте считается возможность записать что-то в данную ячейку, что и подчёркивается с помощью ссылок разного рода.
### `Back in time`: проблема в `C++11`
Итак, мы в `2012` году и у нас нет `auto` для возвращаемого типа функции:
```cpp
template <typename T>
auto // C++11 Error!
makeAndProcessObject(const T& builder) {
	auto val = builder.makeObject();
	// тут auto работает нормально, как описано выше
	// что-то делаем с val
	return val;
}
```
Как же тогда написать данную функцию в реалиях `2012` года, без `auto`?
Руками писать городушку для типа? Проблема в том, что мы заранее тут согласились на разные типы `builder`, т.е. и сам тип `val` в данном случае может быть разным. И что теперь? Может быть `delctype` нам поможет и выведет нам тип выражения? Увы...
```cpp
template <typename T>
decltype(builder.makeObject()) // will fail too
// name builder not in the scope by that moment...
makeAndProcessObject(const T& builder) {
	auto val = builder.makeObject();
	return val;
}
```
#### Решение для `C++11`
В `C++11` разрешили вводить тип возвращаемого выражения уже после того, как разрешены все имена аргументов.

Для решения используется так называемый расширенный синтаксис:
```cpp
int foo(); // обычный синтаксис
auto foo() -> int; // расширенный синтаксис
```

И поправляя нашу проблему:
```cpp
template <typename T>
auto makeAndProcessObject(const T& builder) ->
					 decltype(builder.makeObject()) {
	auto val = builder.makeObject();
	return val;
}
```
#### Решение для `C++14`
Для статического решения можно использовать нефиксированную сигнатуру
```cpp
int foo(); // функция с фиксированной сигнатурой
auto foo(); // функция для которой возвращаемый тип выводится из типа возващаемого через return значения 
```

И поправляя нашу проблему ещё раз, можем уже писать:
```cpp
template <typename T>
auto makeAndProcessObject(const T& builder) {
	auto val = builder.makeObject();
	return val;
}
```

Необходимо помнить, что `auto` продолжает работать ровно по тем же правилам, что и раньше. Т.е. ссылки и константность также режутся по тем же правилам.
#### `Use before deduction`
Бывают случае, когда такой вывод по возвращаемому типу сбивается:
```cpp
auto bad_sum_to(int i){
	// use before deduction
	return (i > 2) ? bad_sum_to(i - 1) + i : 1;
}
```

Более того, для появления данной ошибки не обязательно наличие рекурсии:
```cpp
auto func();

int main() {
	func(); // againg use before deduction
}

auto func() {return 52;} // deduction happening here
```
Тут получается что при использовании данной семантики, как бы изменяется отношение между определением и объявлением функции, для получения сигнатуры нам тут необходимо само тело функции.
#### Обсуждение
Кажется ли вам хорошей идеей нефиксированная сигнатура для внешних `API`, например методов классов в общих хедерах?
(Нет, само собой, это плохая идея)

Именно поэтому даже сейчас форма со стрелочкой используется тогда, когда мы знаем точно, как именно формируется тип:
```cpp
// фиксированная сигнатура, если всё внутри decltype 
// уже известно
auto foo -> decltype(/*some information*/)
```
Так же бывает абсурдное использование этой формы просто для красоты:
```cpp
auto main () -> int { return 42; }
// это не ошибка, но....
```
### Идиома `for-auto`
Обход итератором начиная с `C++11` скрыт за `for-auto` идиомой.
Допустимый вариант:
```cpp
for (auto it = v.begin(), ite = v.end(); it != ite; ++it)
	use(*it);
```

Эквивалентный (почти эквивалентный) вариант:
```cpp
for (auto elt : v) 
	use(elt);
```
Но что если `use` берёт ссылку?
Первый вариант отдаст ссылку, перевязав её.
Второй вариант, увы, срежет тип, значит, скопирует значение.
### Обсуждение: `AAA initializers`
`AAA` - `almost always auto`.

Предложенный Гербом Саттером принцип `AAA` состоит в том, чтобы делать любую инициализацию локальных переменных через `auto`:
```cpp
auto x = 1;
auto y = 1u;
auto c = Customer{"Jim", 42}
auto p = v.cbegin();
```

Начиная с `C++17` он действительно работает (вспоминаем про `prvalue elision`):
```cpp
auto a = std::atomic<int> {9}; // ok только в C++17
// у atomic нет конструктора копирования
// но теперь он тут не вызвается как раз из-за
// обязательно prvalue elision
auto arr = std::array<int, 100> {}; // быстро с C++17
```
Некоторая критика основана на сложности чтения такого кода.
#### Проблемы с `AAA`
**Первое**: 
Не следует тянуть `AAA` в нестатические функции.
Эта идиома только **для инициализации локальных переменных**.
```cpp
auto foo(int x); // non-fixed ABI (from C++14) 

int foo(auto x); // non-fixed ABI (from C++20)
// this will simply be a template
```
**Второе**:
Всё ещё есть случаи, когда это не работает:
```cpp
auto x = long long {42}; // FAIL
// here first long greedly accepted as type by compiler
// but we can avoid it with:
auto x = static_cast<long long> (42); // ok, but...


const int & foo();

auto x = foo(); // decays to int
auto x = static_cast<<const int &>> (42); // still decays to int....
```
# Свертка и проброс ссылок 
## Вывод типов из ссылочных типов
Рассмотрим вывод типов с помощью `auto`:
```cpp
int x;
int &y = x; 

auto &&d = std::move(y); // -> ???
```
Уточнённое с помощью `rvalue-reference`, `auto` не может игнорировать ссылку.

Формально, вывод выглядит так:
```cpp
auto &&c = y; // int & &&c = y;
auto &&d = std::move(y); // int && &&d = move(y):
```
Чтобы в итоге получился корректный тип, ссылки должны быть свёрнуты (`collapsed`).
## Правила свёртки ссылок

| inner | outer | result  |
| ----- | ----- | ------- |
| T&    | T&    | T&      |
| T&    | T&&   | T&      |
| T&&   | T&    | T&      |
| T&&   | T&&   | T&&<br> |
Левая ссылка выигрывает, если она есть
Для примера выше это даёт:
```cpp
auto &&c = y;
// int & && c = y;
// int &c = y;
auto &&d = std::move(y);
// int && && d = move(y):
// int && d = move(y);
```
Правила вывода дают интересную картину:
`auto&` это всегда `lvalue ref`, но вот `auto&&` это либо `lvalue` ref, либо `rvalue ref`(зависит от контекста)
```cpp
auto &&y = x; // x это some& -> y это some&
```
## Универсальность ссылок
### `Универсальные ссылки`
Повторим, что правила вывода дают интересную картину:
`auto&` это всегда `lvalue ref`, но вот `auto&&` это либо `lvalue ref`, либо `rvalue ref`(зависит от контекста)
```cpp
auto &&y = x; // x это some& -> y это some&
```

Но это в целом работает и для `decltype` и для шаблонов (но для шаблонов есть одна техническая трудность):
```cpp
decltype(x) && z = x; // int &z = x;

template <typename T> void foo(T&& t);
foo(x);
// foo<???> (int& t) как думаете, чему тут равен T?
```
Такие ссылки (которые по разному сворачиваются в зависимости от контекста) называют `forwarding references` или `универсальными ссылками`.
### Небольшое уточнение
При сворачивании типов шаблонами мы должны также вывести тип шаблонного параметра:
```cpp
template <typename T> int foo(T &&);
/* 
т.е. вот тут как раз появляется контекст сворачивания
т.е. нам надо понять тип (вывести) -> мы приходим к тому
что необходимо произвести reference collapsing, иначе
тип не легален, а значит теперь уже появляется контекст
для сворачивания, что мы и делаем
*/

int x;
const int y = 5;

foo(x); // -> int foo<int&>(int&)
foo(y); // -> int foo<const int&>(const int&)
foo(5); // -> int foo<int>(int&&)
```
Так как тут тоже присутствует контекст вывода укажем, тип шаблонного параметра выводится по правилам вывода `decltype`.

Т.е. Для консистентности он выводится в ссылку для `lvalue`,но не для `rvalue`.
### Неуниверсальные ссылки
Контекст сворачивания требует **вывода** типов, а не их подстановки:
```cpp
template <typename T> struct Buffer {
	void emplace(T&& param); 
	// это не шаблонный метод у шаблонного класса
	// в конструкторе да, вывод есть, но коструктор - 
	// метод особый
	
	// здесь T подставляется
	
	// ведь он уже известен и не зависит от типа аргумента,
	// который прокинут в функцию
};

template <typename T> struct Buffer {
	template <typename U>
	void emplace(U&& param); 
	// это шаблонный метод у шаблонного класса
	
	// здесь U выводится
	
	// тут наобарот, у данной функции	
	// свой тип U, который будет выведен из 
	// типа аргумента, он же не совпадает с 
	// типом класса
};
```

**Контекст для сворачивания не будет создан**, 
если тип уточнён более, чем `&&` (наример, `const &&`):
```cpp
const auto &&x = y; // никакого сворачивания ссылок

template <typename T> void buzz(const &&T param);
// аналогично, сворачивания не будет
```

Но куда лучший вариант:

Он лишён недостатков, которые мы заметили ранее.

## Прозрачная оболочка
Представим теоритическую задачу сделать функцию максимально "прозрачной" то есть пробрасывающей свои аргументы без расходов:
```cpp
template <typename Fun, typename Arg>
??? transparent (Fun fun, Arg arg) {
	return fun(arg);
}
```
Начнём с того, что же она возвращает?
Она может возвращать как левую, так и правую ссылку.
Знакомтесь...
### `decltype(auto)`
Совмещает ~~худшие~~ лучшие стороны двух механизмов вывода.

Вывод типов является точным, но при этом выводится из всей правой части (т.е. правила `decltype`, но выражение для вывода берётся справа):
```cpp
double x = 1.0;

decltype(x) tmp = x; // два раза x не нужен
decltype(auto) tmp = x; // это именно то, что нужно
```

Однако, что стоит справа, `expr` или `id-expr`? 
Зависит от выражения...
```cpp
decltype(auto) tmp = x; // -> double
decltype(auto) tmp = (x); // -> double&
```
Не пользуйтесь этой штукой, если точно не понимаете, зачем её используете.

Но в нашем примере мы же понимаем)):
```cpp
template <typename Fun, typename Arg> 
decltype(auto) transparent (Fun fun, Arg arg) {
	return fun(arg);
}
```
Увы, но её недостаток теперь в том, что она не слишком то и прозрачна:
```cpp
extern Buffer foo(Buffer x);

Buffer b;
Butter t = transparent (&foo, b); 
// тут явное копирование b
```
## Снова прозрачная оболочка
**Возможный выход**: сделать аргумент ссылкой:
```cpp
template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, Arg &arg) {
	return fun(arg);
}
```

Но появляется новая проблема, `rvalue` не пролезают в функцию:
```cpp
extern Buffer foo(Buffer x);

Buffer b;
Butter t = transparent (&foo, b); // ок
Butter u = transparent (&foo, foo(b)); // ошибка компиляции
```

**Возможный выход**: перегрузить по константной ссылке:
```cpp
template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, Arg &arg) {
	return fun(arg);
}

template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, const Arg &arg) {
	return fun(arg);
}
```
```cpp
extern Buffer foo(Buffer x);

Buffer b;
Butter t = transparent (&foo, b); // ок
Butter u = transparent (&foo, foo(b)); // пойдёт, компилируется хотя бы 
```
Но есть проблемы:
- Всего `10` аргументов потребую `1024` перегрузки для данной функции
- Вызов для `rvalue` всё ещё требует копирования

**Возможный выход**: универсализовать ссылку:
```cpp
template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, Arg &&arg) {
	return fun(arg);
}

extern Buffer foo(Buffer x);

Buffer b;
Butter t = transparent (&foo, b); // ок
Butter u = transparent (&foo, foo(b)); // ok, но всё ещё копирует
```
Но есть проблемы:
- ~~Всего 10 аргументов потребую 1024 перегрузки для данной функции~~
- Вызов для `rvalue` всё ещё требует копирования

## Чего бы нам хотелось
**Решение для второй проблемы**: условное перемещение
```cpp
template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, Arg &&arg) {
	if (/*arg это rvalue*/)
		return fun(std::move(arg));
	else 
		return fun(arg);
}

Buffer b;
Butter t = transparent (&foo, b); // ок
Butter u = transparent (&foo, foo(b)); // ok
```
Это бы решило часть проблем, но это не легальный `С++`.
Хотя, постойте...
## Решение: использовать `std::forward`
**Решение для второй проблемы**: условное перемещение
```cpp
template <typename Fun, typename Arg> decltype(auto) 
transparent (Fun fun, Arg &&arg) {
	return fun(std::forward<Arg>(arg));
}

Buffer b;
Butter t = transparent (&foo, b); // ок
Butter u = transparent (&foo, foo(b)); // ok
```
Это называется `perfect forwarding` и бывает удивительно полезной идиомой.

Три главных составляющих `perfect forwarding`:
1. контекст вывода типа `T`
2. тип `T&&`
3. `std::forwar d<T>`
## Обсуждение: `emplace`
Что если мы пробросим аргументы **для конструктора**?
```cpp
MyVector<Heavy> vh;

vh.push(Heavy{100}); // создаёт, потом перемещает

vh.emplace(100); // пробрасывает, создаст на месте 
```
Это может существенно сократить количество операций. 
Внезапно, настоящий `std::vector` это умеет и более того, умеет принимать произвольное количество аргументов конструктора.
