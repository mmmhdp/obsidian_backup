# Обработка ошибок в стиле C
Определяется область целочисленных кодов ошибок:
```cpp
enum error_t = {E_OK = 0, E_NO_MEM, E_UNEXPECTED};
```
Сообщить об ошибке можно следующими путями:
- Вернуть код ошибки:
  ```cpp
 error_t open_file (const char * name, FILE **handle);
  ```
- Использует thread-local facility, например errno/GetLastError:
```cpp
FILE * open_file (const char * name);
```
- Берёт error_t* в списке параметров:
  ```cpp
  FILE * open_file (const char * name, error_t * errcode)
  ```

# Основная идея решения вопроса
- Выйти из вызванной функции в вызывающий код в обход обычных механизмов возврата управления.
- Аннотировать этот **нелокальный** выход информацией о случившемся
- Но что вообще мы знаем о нелокальных переходах?
## Типы передачи управления
### Локальная передача управления
- условные операторы
- циклы
- локальный goto
- прямой вызов функций и возврат из них
### Нелокальная передача управления

- нелокальный longjmp и вычисляемый goto

# Исключения
Для начала, определимся с терминами.

Термин "исключения" возникает в следующих контекстах:
- Исключительные ситуации уровня аппаратуры (например undefined instruction exception)
- Исключительные ситуации уровня операционной системы (например data page fault)
- Исключения С++ (только они нас будут интересовать далее)

Дабы прочувствовать разницу между этим вещами, можно сказать, что разрабатывая прикладную программу на C++ мы взяли книгу по садоводству и капаем свой садик. Но садик наш, к сожалению, находится на склоне вулкана.

Первые два пункта - это извержение того самого вулкана, книжка по садоводству тут нам ничем помочь не может.

Последний пункт - это условный камешек в нашей грядке, тут мы действительно можем что-то сделать и обработать данную ситуацию.

## Исключительные ситуации
- Ошибки (исключительными ситуациями не являются)
	- рантайм ошибки, после которых состояние не восстановимо (например segmentation fault) 
	- ошибки контракта функций (assertion failure из-за неверных аргументов, невыполненые предусловия вызова)
- Исключительные ситуации
	- Состояние программы должно быть восстановимо (например: исчерпание памяти или отсутствие файла на жёстком диске)
	- Исключительная ситуация не может быть обработана на том уровне, на котором возникла (программа сортировки не обязана знать, что делать в ситуации отсутствия памяти на дополнительный буфер, который необходим в процессе сортировки)

## Больше про throw
Конструкция throw \<expression\> означает следующее:
- Создать объект исключения 
- Начать размотку стека

Примеры:
```cpp
throw 1;

throw new int(1);

throw MyClass(1, 1);
```

Исключения отличаются от ошибок тем, что их нужно **ловить**.

## Ловля исключений
Производится внутри try блока:
```cpp
int divide (int x, int y)
{
	if (y == 0) throw OVF_ERROR; // так себе идея
	return x / y; 
}

// где-то далее

try 
{
	int c = divide (a, b);
	
} catch (int errcode) {
	if (errcode == OVF_ERROR)	
		std::cout << "Overflow" << std::endl;
}
```

### Некоторые правила
**Ловля ислючений происходит по точному типу.**

Буквально любые implicit преобразования тут не работают, выжило только преобразование Derived в Base. Даже enum в int - не скастуется.

Также важно помнить, что временный объект исключения всегда является lvalue, т.е. ловить по правой ссылке не получится никогда.

- Ловля ислючений происходит по точному типу:
  ```cpp
  try {throw 1;} catch (long err){}; // не поймали
  ```
- Или по ссылке на точный тип:
  ```cpp
  try {throw 1;} catch (const int &err){}; // поймали
  ```
- Или по указателю на точный тип:
  ```cpp
  try {throw new int(1);} catch (int *err){}; // поймали
  ```
- Или по ссылке или указателю на базовый класс:
  ```cpp
  try {throw Derived();} catch (Base  err){}; // поймали
  try {throw Derived();} catch (Base &err){}; // поймали
  try {throw Derived();} catch (Base *err){}; // поймали
  ```

**Catch-блоки пробуются в порядке перечисления:**
```cpp
try {throw 1;}
catch (long errcode) {} // не поймали
catch (const int & errcode) {} // поймали
```

**Пойманную переменную можно менять или удалять:**
```cpp
try {throw new Derived();} 
catch (Base *b) {delete b;} // ok
```
Владельцем объекта исключения считается пользователь, а значит за память, выделенную через new отвечать тоже ему. 

Поэтому кидать так исключения - это плохая практика

**Два исключения в обработке вызывают std::terminate.**
Что приводит нас к разным техникам обработки нескольких исключений.
Спойлер - мы их складываем в контейнер и пробрасываем дальше уже его.

**Пойманное исключение можно перевыбросить:**
```cpp
try {throw Derived();}
catch (Base &b) {throw;} // ok
```
Пример применения - мы поймали исключение и не знаем, что с ним делать, прокидываем его дальше по стеку, может быть оно должно быть обработано на другом уровне.

## Интерфейс std::exception
```cpp
struct exception {
	exception() noexcept;
	exception(const exception &ex) noexcept;
	exception& operator=(const exception &ex)	noexcept;
	
	virtual ~exception();
	// деструктор всегда noexcept, т.е. его можно не аннотировать
	virtual const char * what() const noexcept;
};
```
noexcept - аннотация, которая говорит о том, что функция не выбрасывает исключений. Если оно таки вылетит из аннотированной noexcept функции - std::terminate.

noexcept распространяется и на переопределения виртуальных функций.
Подробнее о нём позже.

## Перехват всех исключений
Используется троеточие, как для va_arg:
```cpp
try {
// опасный код
} catch (...){
// тут обработка ВСЕХ исключений
}
```
Конечно, идеи хоть как-то обработать любое исключение очень сомнительна.
Более того, проблема такой в конструкции в том, что мы можем поймать так те исключения, которые могут быть обработаны дальше по стеку, но до них не дойдёт, так как мы ловим абсолютно всё.

Единственно разумный вариант использования - это rethrow с каким-то дополнительным эффектом - например, освобождение выделенного ресурса.
Но тут возникает резонный вопрос - а почему у нас вообще есть голый указатель на выделенный ресурс, если оно должен управляться RAII классом. Вопрос философский.
## Нейтральность относительно исключений
Функция называется нейтральной относительно исключений, если она не ловит чужих исключений.

Хорошо написанная функция в хорошо спректированном коде, как минимум нейтральна.

## Try-блоки уровня функций
Но всё ещё не ясно, зачем нам тогда вообще catch(...), ведь кажется, что мы должны избегать его любыми способами. Всё так, но есть места, из которых иным способом поймать исключения невозможно. Например, список инициализации.

Тогда мы можем запихнуть целую функцию в try-блок:
```cpp
int foo() try { bar(); }
catch (std::exception &e) {throw;}
```
В том числе и конструктор:
```cpp
Foo::Foo(int x, int y) try : x_(x), y_(y) {
	// some actions
}
catch (std::exception& e) {
	// some processing
}
```

Техника экзотическая, но лучше знать, чем нет.
### Catch уровня функци
На уровне функции, catch входит в scope функции:
```cpp
int foo(int x_scoped_to_foo) try {
	bar();
} catch (std::exception &e){
	std::cout << x_scoped_to_foo << ":" << e.what() << std::endl; // ok
}
```

Увы, но try-блок на функции main не поймает исключения, которые выброшены при создании глобальных объектов, что является ещё одним поводом для отказа от использования подобных объектов в программе.
# Безопасность исключений
## Постановка проблемы: пример Каргилла
```cpp
template <typename T> class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	
public:
	MyVector (const MyVector &rhs) {
		arr_ = new T[rhs.size_];
		size_ = rhs.size_; used_ = rhs.used_;
		
		for (size_t i = 0; i != rhs.size_; ++i)
		{
			arr_[i] = rhs.arr_[i];
			/*
				Данная точка в программе является не 
				безопасной относительно исключения, которое
				тут может появится при вызове конструктора
				копирования, так как заранее на тип T тут
				нет ограничений, а значит там может вылететь
				исключение.
				
				Проблема в том, что ресурс arr_, который тут
				выделен, не будет освобождён и попросту 
				утечёт. Более того, данная утечка может 
				повторятся неоднократно, так как ошибка 
				может быть обработана в пользоватеском коде 
				ну и вызвана повторно в дальнейшем само 
				собой.
			*/
		}
	}
};
```
Цену работы с исключениями, которая на самом деле во многом состоит не в накладных расходах на обработку, а в интеллектуальных расходах на рассмотрение кода, путь исполнения которого может перенестись в другую точку исполнения (code path disruption), поняли не сразу, но поняли.

Вообще, это важная часть понимания кода человеком - когда есть возможность тривиально оценивать путь исполнения в программе, а тут выходит, что исключения могут прервать поток исполнения в неожиданные моменты.

Всё это нас приводит к тому, что код с исключениями имеет некую особую природу, нам необходимо думать о том, как писать программы, которые безопасны относительно исключений. Обсудим критерии этой безопасности.
## Гарантии безопасности исключений
**Базовая гарантия**:
Исключение при выполнении операции может изменить состояние программы, но не вызовет утечек и оставляет все объекты в согласован (**НЕ ОБЯЗАТЕЛЬНО ПРЕДСКАЗУЕМОМ**) состоянии.

**Строгая гарантия**:
При исключении гарантируется **неизменность состояния** программы относительно задействованых в операции объектов (commit\rollback).

**Гарантия бессбойности**:
Функция вообще не генерирует исключений, что мы гарантируем с помощью noexcept.

## Безопасное копирование
```cpp
template <typename T> class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	
public:
	MyVector (const MyVector &rhs) {
		tmp = new T[rhs.size_];
		
		try {
			for (size_t i = 0; i != rhs.size_; ++i)
			{
				tmp[i] = rhs.arr_[i];
			}
		} catch (...){
			delete tmp;
			throw;
		}
		
		size_ = rhs.size_; used_ = rhs.used_;
		arr_ = tmp;
	}
};
```
Это лучше, но это хрупко. Можно лучше

## Внезапно swap
В примерах ранее обсуждаля не только конструктор копирования, но и оператор присваивания. Суть одна, поэтому я не привёл пример с оператором, но этот код - это именно продолжения об улучшении оператора присваивания.
```cpp
template <typename T> class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	/* 
	1) 
		интересно, что все поля тут такого типа
		что операции с ними не бросают исключения
	*/ 
	
public:
	void swap(MyVector &rhs) noexcept
	/* 
		1) тогда задокументируем это и компилятор
		   сможет провести дополнительные оптимизации
	*/
	{
		std::swap(arr_, rhs.arr_);
		std::swap(size_, rhs.size_);
		std::swap(used_, rhs.used_);
		// 2) swap тоже не просает исключения
	}
};
```

## Линия Калба
Подход к проектированию с исключениями от Калба.
В любом методе вы должны провести ментально линию (иногда не одну),
выше которой может быть выброшено исключения, а ниже которой может быть изменено сотояния класса. 
```cpp
template <typename T> class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	/* 
	1) 
		интересно, что все поля тут такого типа
		что операции с ними не бросают исключения
	*/ 
	
public:
	void swap (MyVector &rhs) noexcept;
	
	MyVector& operator=(const MyVector &rhs)
	{
		MyVector tmp {rhs}; // тут ещё может быть исключение
--------------------------------------------------------	
		swap(tmp); 
		// а тут мы уже можем менять состояние класса 
		return *this;
	}
};
```
Так мы даём строгую гарантию безопасности для оператора присваивания.

## Правило для деструкторов
**Исключения не должны покидать деструктор!**

По стандарту, исключение, покинувшее деструктор, если при этом остались необработанные исключения, приводит к вызову std::terminate и завершению программы.

## Условный `noexcept`
Ранее мы рассмотрели `noexcept` как аннотацию.
Проблема в том, что частно не совсем ясно, будет ли верна `noexcept` аннотация для данной функции:
```cpp
template <class T> 
T copy(T const &src)
/*
 noexcept работает в данном случае для фундаментальных типов
 и в этом уверенность есть, но для остальных мы не можем
 дать такую гарантию, т.е. мы хотим noexcept с условием...
*/

{
	return orig; // dummy code, but it's not matter	
}
```

И тут приходит на помощь условная форма аннотации `noexcept`, которая
позволяет это сделать:
```cpp
template <class T> 
T copy(T const &src)
noexcept(is_fundamental<T>::value)
{
	return orig; // dummy code, but it's not matter	
}
```

Пояснение к формам такой аннотации:
```cpp
noexcept(true);
// тоже самое, что и просто noexcept

noexcept(false);
/*
 это отсутствие noexcept, а не обещаение, что функция 
 точно ничего не бросит. Необходимость в таком механизме
 присутствует, так как деструкторы имеют данную аннотацию 
 по умолчанию, И ЕСЛИ ВЫ ТАКИ РЕШИЛИСЬ ВЫСТРЕЛИТЬ СЕБЕ
 В КОЛЕНО, то тогда можно пробросить исключение из 
 деструктора.
*/
```

Интересно, что наше решение проблемы всё равно выглядит не очень, данным условием мы покрываем не всё, что хотели бы, а гораздо больше, так как на самом деле не только фундаментальные классы могут иметь конструктор копирования с noexcept гарантией.
## Оператор noexcept
Оператор noexcept вычисляет тип на этапе компиляции и возвращает 
true или false в зависимости от результата.

```cpp
template <typename T>
T copy(T const &orig) 
noexcept // это аннотация для copy
/*
	дело в том, что 
	noexcept(true)	<=> noexcept
	noexcept(false) <=> ""
	как мы обсудили выше.
	
	а выражение с оператором noexcept()
	возращает как раз те самые true или false,
	а значит мы получаем на руки странную, но
	логичную связку noexcept ((noexcept (expr)), которая даёт нам опциональный noexcept в зависимости
	от того, бросает или нет выражение expr
*/
(
noexcept(T(orig)) 
/*
 оператор, который проверяет явно наличие copy 
 конструктора у типа T, а неявно он проверяет наличие
 небросающего деструктора, так как это самое T потом
 должно умереть ещё в конце выражения.
*/

) 
{
	return orig;
}
```

Разумеется, выражение вида T(orig) выглядит так себе.
Есть более подходящие формы для выражения нашего намерения:
```cpp
template <typename T>
T copy(T const &orig) 
noexcept(
	std::is_nothrow_copy_consturctible<T>::value) {
	return orig;
}
```
Внутри этот определитель реализован через оператор noexcept и настоящее место данного оператора - внутри библиотечного кода. Но знать о нём полезно в любом случае.
### Оператор noexcept : детали
Оператор noexcept на самом деле не вычисляет, а оценивает каждую функцию в выражении.

```cpp
struct ThrowingCtor {
	ThrowingCtor(){}
	/*
		Но ctor ничего не бросает, но как было сказано,
		функция оценивается, а не вычисляется, что
		выражается в том, что на самом деле компилятор
		просто смотрит на аннотацию.
		
		Нет аннотации - значит может бросить исключение.
	*/
};

void foo(TrowingCtor) noexcept;
void foo(int) noexcept;

assert(noexcept (foo(1)) == true);
assert(noexcept (foo(ThrowingCtor{})) == false);
```

Интересно, что разыменование nullptr это вариант нормы для noexcept.
```cpp
auto res = noexcept (*static_cast<int *>(nullptr));
/*
	тут не будет UB, производится оценка выражения,
	а не его вычисление.
	
	интересно, что с interpret_cast это уже UB, данный 
	каст запрещено использовать в выражениях этапа 
	компиляции. 
	
	Моменты, связаные с этапом компиляции и его 
	особенностями будут позже в курсе.
*/
assert(res == true); // как не странно
```
### Обсуждение: `noexcept(false)`
Любой деструктор по умолчанию - `noexcept`.
Одним из способов позволить исключениям покидать деструктор является пометка его как `noexcept(false)`.

Вы должны быть очень осторожны, помечая так деструктор, так как он сам вызывается в процессе размотки другого исключения.

Но, вы можете проверить внутри деструктора, идёт сейчас размотка стека или нет с помощью вызова:
```cpp
std::uncaught_exceptions()
```

## Безопасность исключений: извлечение из массива
```cpp
template <typename T> 
class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	
public:
	T pop(){
		if (used_ <= 0) throw e_underflow{};
		T result = arr_[used_ - 1];
		------------------
		used_ -= 1;
		return result;
	}
};
```
Кажется, что данный код организован верно относительно линии Калба и всё такое. И это правда так. 

Засада ожидает нас не в фунции pop, а в той, куда она вернёт значение.
Дело в том, что в данном случае мы возвращаем result по значению, 
что автоматически значит, что для передачи и сохранения его в переменную будет вызван copy ctor или operator=.

А про него мы ничего не знаем, а значит, он как раз и может выкинуть исключение. Тогда переданный объект будет уничтожен ещё до того, как мы его смогли записать в переменную, т.е. он утерян навсегда:
```cpp
using ST = SomeTypeWithExcInCopyConsturctorOrAssignOp;
MyVector<ST> v;

// много кода

ST s = v.pop(); // исключение при копировании s
```

Правда в том, что данный код просто плохо спроектирован и реальный интерфейс вектора в стандартной библотеке выглядит иначе именно из-за проблемы с безопасностью исключений.
## Безопасность исключений: извлечение из массива v2
Правильное проектирование страхует нас от подобных проблем:
```cpp
template <typename T> 
class MyVector {
	T *arr_ = nullptr;
	size_t size_, used_ = 0;
	
public:
	T top() const {
		if (used_ <= 0) throw e_outofbounds{};
		return arr_[used_ - 1];
	}
	/*
		------------------------
		Somewhat like Calb like is here,
		between the functions	
	*/

		used_ -= 1;
	}
};
```

Оказывается, что безопасность относительно исключений влияет на проектирование! Если это так, то почему бы сразу не спроектировать нечто, что нам удобно будет делать безопасным? Удивительно, но для ответа на данный вопрос необходимо погрузиться в тонкости работы с памятью.

# Детали работы с памятью
## Глобальные операторы
В языке `C` для выделения память служат функции `malloc` и `free`:
```c
void *p = malloc(10);
free(p);
```
В языке `C++` этим занимаются операторы `new` и `delete`.
При этом, скажем, в отличии от оператора +, у них есть **глобальные формы**.

Когда вы пишите `new-expression` для встроеного типа, он будет истолкован именно как вызов глобального оператора:
```cpp
int *n = new int(5);
// выделение + конструирование

n = (int *) ::operator new(sizeof(int)); 
// только выделение памяти
```

Данные операторы можно перегружать, изменяя поведение всех классов, которые ими пользуются:
```cpp
void *operator new(std::size_t n)
{
	void *p = malloc (n);
	if (!p)
		throw std::bad_alloc{};
	printf("Alloc: %p, size is %zu\n", p, n);
	/*
	 printf - так как мы уверены, что он не выделяет 
	 под себя память, мы тут боимся бесконечной рекурсии
	*/
	
	return p;
}

int main() { std::list<int> v; v.push_back(52); }

/*
 на экране:
 Alloc: 0x639ed7ced2b0, size is 24
 
 24 - размер узла в list
*/
```

## `new` и создание массива объектов
Мы отделяем вызов конструкторов от выделения памяти, но что если конструктор выбросит исключение?
```cpp
struct S {
	S(); // десятый конструктор кинет исключение
	~S();
};

S *sarr = new S[15];
```

Ответ прост - столько, сколько вызвано было конструкторов.
Оператор `new` даёт строгую гарантию исключений, а значит обязан не просто освободить память, но и вызвать соответствующие деструкторы у уже созданных объектов.

## Формы глобальных операторов
Основные формы чем-то похожи на `malloc`:
```cpp
void *operator new(std::size_t);
void operator delete(void *) noexcept;
void operator new[](std::size_t);
void operator delete[](void *) noexcept;
```

Предусмотрены также дополнительные варианты с семантикой `noexcept`:
```cpp
void * operator new  (
	std::size_t, const std::nothrow &) noexcept;
void * operator new[](
	std::size_t, const std::nothrow &) noexcept;
```

## Небросающий `new`
Если для `new-expression` не передано аргументов, оно раскрывается просто:
```cpp
p = new int {42};
// p = (int *) :: operator new(sizeof(int)); *p = 42
```

Если аргументы переданы, они ставятся в конец глобального оператора:
```cpp
p = new (nothrow) int {42};
/*
p = (int *) :: operator new(sizeof(int), nothrow);
if(p):
	*p = 42
else:
	return nullptr;
*/
```
Специальный аргумент `std::nothrow` типа `std::nothrow_t` показывает, что мы не хотим бросать исключения из оператора. Это `malloc-style` подход, а значит, при неудачном выделении возвращаемым значением будет нулевой указатель, который необходимо будет проверить уже в вызывающем коде.

## Размещающий `new` (`placement new`)
Поскольку аллокация/деаллокация это операторы, они могут быть переопределены.

Но есть непереопределяемый глобальный оператор:
```cpp
void * operator new(std::size_t, void *ptr) noexcept;
void * operator new[](std::size_t, void *ptr) noexcept;
```

Он называется размещающий `new` и ему не соответствует никакого `delete`, потому что всё, что он делает, это размещает объект в сырой памяти.

### Работа с размещающим `new`
Работа с памятью может быть отделена от работы с объектом памяти:
```cpp
void *raw = ::operator new (sizeof(Widget)), std::nothrow);
if (!raw) {
// обработка
}

Widget *w = new (raw) Widget{};

// тут использование w;

w->~Widget();
::operator delete(raw);
```
Данная возможность даёт нам новые инструменты для построения кода, который безопасен относительно исключений. 

## Переопределение new и delete на уровне класса
Замечательным свойством new и delete является возможность переопределить их не глобально, а на уровне своего класса.

```cpp
struct Widget {
	static void *operator new(std::size_t n);
	static void operator delete(void *mem) noexcept;	
};
```
Теперь для класса Widget будут использоваться его собственные операторы, а не глобальные.

При этом, локальные для класса размещающий new может быть переопределён, в отличии от глобальной версии этого оператора.

## Работа с пользовательским классом
Проведём небольшую ревизию.

- new с исключениями при исчерпании памяти
```cpp
Widget *w = new Widget{};
```
- new с возвратом нулевого указателя
```cpp
Widget *w = new (nothrow) Widget{};
if (!w)
{
	// обработка
}
```
- размещающий new
```cpp
void *raw = ::operator new (sizeof(Widget)); 
// тут возможен bad_alloc;

Widget *w = new (raw) Widget{};
```

Интересно то, что это условно стандартные формы оператора new, скажем "ожидаемые формы". Дело в том, что пользовательский оператор new может быть перегружен с любым количеством аргументов. Делать так не стоит, но кого это останавливает...

## Развитие идеи
В лекции тут появляется код, который реализует эти объекты.
Рассмотрим метод push:

void MyVector::push(const T& t) {
	if (used_ == size_){
		MyVector tmp (size_* 2 + 1);
		while (tmp.size_ < used_) {
			 tmp.push(arr_[tmp.size()]);
			 /*
				 Тут мы копируем, но потом мы избавился 
				 от tmp. 
				 
				 Может тогда лучше использовать 
				 перемещение?
			 */
		}
		tmp.push(t);
		-------------------------------------------
		// пока линия калба проходит тут

		swap(*this, tmp);

### Первая проблема: константность
Придётся подублировать код, чтобы аккуратно работать с константностью:
```cpp
void MyVector::push(const T& t) {
	T t2(t);
	push(std::move(t2));
}

void MyVector::push(T&& t) {
	if (used_ == size_){
		MyVector tmp (size_* 2 + 1);
		while (tmp.size_ < used_) {
			 tmp.push(std::move(arr_[tmp.size()]));
			 // перемещение
		}
		tmp.push(std::move(t));
		swap(*this, tmp);
	}
}
```

Код не лучший, но он тут для того, чтобы показать, что проблема решаема.

Нюанс в том, что это действительно лучше, чем было, только тогда, 
когда move не бросает исключений, иначе ничего особо и не решилось.

### Вторая проблема: линия Калба
```cpp
void MyVector::push(const T& t) {
	T t2(t);
	push(std::move(t2));
}

void MyVector::push(T&& t) {
	if (used_ == size_){
		MyVector tmp (size_* 2 + 1);
		------------------------------
		/*
		 должна быть тут, так как ниже мы уже начинаем
		 менять инварианты класса.
		 но если move бросит, то тогда мы уже не знаем,
		 где реально проводить линию Калба...
		*/
		while (tmp.size_ < used_) {
			 tmp.push(std::move(arr_[tmp.size()]));
		} tmp.push(std::move(t));
		------------------------------
		// ранее была здесь
		swap(*this, tmp);
	}
	
}
```

### Решение
Решение напрашивается само собой - так может такой конструктор и не должен бросать исключений? Оказывается, так оно и есть.

Перемещающие конструкторы и присваивания не должны бросать исключений:
```cpp
MyVector (MyVector &&rhs) noexcept = default; 
MyVector& operator= (MyVector &&rhs) noexcept = default; 
```

При этом, если они неправильные или их попросту нет, копирование неизбежно, что сделает наш код менее эффективным:
```cpp
void MyVector::push (const T& t){
	if (std::is_nothrow_move_assignable<T>::value)
		push_move(t);
	else
		push_copy(t);
}
```
