# Последовательные контейнеры
**Контейнеры**:
- `vector` - есть гарантия по памяти.
массив с переменным размером и гарантией непрерывности памяти
- `array` - есть гарантия по памяти.
массив с фиксированным размером, известным в момент компиляции
- `deque`
массив с переменным размером без гарантий по памяти
- `list`
двусвязный список
- `forward_list`
односвязный список

**Адаптеры**:
- `stack`
FIFO контейнер, чаще всего на базе `deque`
- `queue`
LIFO контейнер, чаще всего на базе `deque`
- `priority_queue`
очередь с приоритетами, чаще всего на базе `vector`

## Что может смущать в этом коде?
```cpp
std::deque<int> d; // а если бы тут был вектор?

for (int i = 0; i != N; ++i)
{
	d.push_front(i);
// если вектор, то тут у операции O(n) сложность
	d.push_back(i);
// если вектор, то тут будут возникать потенциальные 
// реаллокации в неизвестном количестве
}

// Но использование deque лишает нас всех этих забот
// push_front() - O(1)
// гарантий по памяти нет - так что перевыделять не нужно
// т.е. push_back() - O(1), а не O(1+)
// поэтому тут всё хорошо
```
## Рассмотрите `deque` вместо `vector`
Про `deque`:
- Эффективно растёт в обоих направлениях
- Не требует больших реаллокаций с перемещениями, так как разбит на блоки
- Гораздо меньше фрагментирует кучу

## Деки против векторов

| Вектора                        | Деки                                       |
| ------------------------------ | ------------------------------------------ |
| Доступ к элементу за `O(1)`    | Доступ к элементу за `O(1)`                |
| Вставка в конец аморт. `O(1)+` | **Вставка в конец `O(1)`**                 |
| Вставка в начало `O(n)`        | **Вставка в начало `O(1)`**                |
| Вставка в середину `O(n)`      | Вставка в середину `O(n)`                  |
| Вычисление размера `O(1)`      | Вычисление размера `O(1)`                  |
| **Есть гарантии по памяти**    | Нет гарантий по памяти                     |
| Есть `reserve/capacity`        | **Нет необходимости в `reserve/capacity`** |
Но интересно, что на практике замеры показывают, что на самом деле доступ к элементу у деки примерно на `30%` медленне, чем у вектора, та самая константа прилично больше у деки.
## Обсуждение
Допустим, вас просят реализовать вот такой контейнер:
- "`deque is the data structure of choice then most insertions and deletions take place at the beginning or at the end of the sequence`"
Как бы вы его реализовали?
Ответ - массив из указателей не блоки, плюс указатель на текущее положение. Тогда и доступ за `O(1)`, хотя и с косвенностью большой, что и даёт просадку по сравнению с вектором, а с другой стороны вставки 
упрощены для такой структуры до `O(1)`. Т.е. всё необходимое на месте.

## Особая возвожность списков: итераторы
У списков никогда не инвалидируются итераторы после операций, что позволяет найти для них применение, когда нам важно сохранить итераторы и использовать их в дальнейшем.

Пример - lru-cache, иначе, как списком там не воспользоваться, так как в итоге нам необходимо хранить указатели на элементы, это то что мы делаем в C, а сейчас мы будем хранить вместо них итераторы на один из видов списка и получать такой же результат.
## Особая возвожность списков: splice
![[Pasted image 20260106113041.png]]
### Сплайс для списков: простая форма
Сложность `O(1)`
```cpp
forward_list<int> fst = {1, 2, 3};
forward_list<int> snd = {10, 20, 30};
auto it = fst.begin(); // указывает на 1

// перемещение second в начало first, it указывает на 1
fst.splice_after(fst.before_begin(), snd);
```
![[Pasted image 20260107103636.png]]
### Сплайс для списков: сложная форма
Сложность `O(n)`
```cpp
forward_list<int> fst = {10, 20, 30 ,1, 2, 3};
forward_list<int> snd = {};

// it всё ещё указывает на 1

// перекидываем элементы со второго по it в список second
snd.splice_after(snd.before_begin(), fst, fst.begin(), it);
```
![[Pasted image 20260107104000.png]]
### Сплайс для списков: средняя форма
Сложность `O(1)`
```cpp
forward_list<int> fst = {10,,1, 2, 3};
forward_list<int> snd = { 20, 30 };
// it всё ещё указывает на 1

// все элементы второго списка начиная со второго в первый
fst.splice_after(fst.before_begin(), snd, snd.begin());
```

## Обсуждение: usecase списков
- Ранее уже говорили о том, что итераторы не инвалидируются у списков, а значит, их списки можно применять, где есть в таком необходимость
- Банальная экономия - в списке, с учётом отсутсвия инвалидации опять же, можно хранить информацию о массивных объектах, при этом тратить на эту информацию разительно меньше места

### Виды адаптеров
Казалось бы, оба эти контейнера реализуются на `deque`, но у них есть особенности, которые выделяют их - например, `stack` как адаптер по умолчанию действительно использует `deque` как базовый контейнер, но на самом деле `stack` может быть обёрткой для любого контейнера с определённым интерфейсом. Тоже относится и к другим адаптерам.

Идея в том, что мы явно указываем то, что в данной ситуации контейнер должен иметь лишь урезанный до адаптера интерфейс.
- `stack` - `LIFO` стек над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = deque<T>
> class stack;
```
- `queue` - `FIFO` очередь над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = deque<T>
> class queue;
```
- `priority_queue` - очередь с приоритетами (как `binary heap`) над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = vector<T>,
	typename Compare = less<typename Container::value_type>
> class priority_queue;
```
### Защита от ортогональности
```cpp
std::stack<int> s; // ок, это stack <int, deque<int>>
std::stack<int, std::vector<long>> s1; // сомнительно
std::stack<int, std::vector<char>> s2; // совсем плохо 

s2.push(1000);
// а что тогда вернёт s2.top()?
```
К счастью, подобное безобразите покрыто `static_assert`'ами
### Недостаточная ортогональность
```cpp
std::stack<int, std::forward_list<int>> s; // ок

s.push(100); // ошибка: нет push_back
s.pop(); // ошибка: нет pop_back
s.top(); // ошибка: нет back
```
Эти ошибки не очевидны, стек то вполне может быть сделан на односвязном списке. Но дело в том, что адаптер `stack` требует (неявно) вполне определённый интерфейс от внутреннего контейнера.
## Обсуждение
- Почему `stack`,`queue` и `priority_queue` не являются отдельными контейнерами?
Плюсы смены контейнера идут от особенностей контейнера. Например, если мы уверены, что размер стека будет меняться нечасто и малыми шагами, а также хотим увеличить локальность кэша - то положить вектор место деки в основу - хорошая идея.
- И почему тогда двухголовая очередь - `deque`, не является адаптером? 
Ответ от лектора - кажется, что корневое отличие адаптера от контейнера состоит в том, как контейнеры работают с памятью, именно в этом разница - у каждого контейнера свой специфичный подход к организации памяти.
# Контейнеро-подобные классы
Конкретные классы которые удобно использовать для конкретных задач.

## `bitset`
`bitset` - это альтернатива `array<bool>` то есть у него фиксированный размер, являющийся параметром контейнера.
При этом, он хранит данные более компактно (как `vector<bool>`)
```cpp
// 24-bit number
bitset<24> s1 = 0x7ff000;
bitset<24> s2 = 0x00ff00;

s1[0] = 1; // или s1.set(0) или s1.set(0, 1)

auto s3 = s1 & s2; // s3 = 0xf000
```
По сути он делает `array<bool>` (который не оптимизирует хранение, а честно хранит каждое значение в отдельном `char`'е) не нужным.
## `string`
### Обсуждение: поговорим о строках

- Почему специальный `std::string`(конечно, это алиас, тут должен быть `std::basic_string<char>`) а не `vector<char>`?
  *Важная ремарка*: формально `std::string` это непрерывный контейнер, имеющий с вектором много общего.
Ответ банальный - строки специфичны, а значит, нам бы хотелось иметь особый, привязанный к строкам интерфейс для работы с ними.
### Строки: базовая функциональность
Сравним со старым добрым C-style работой со строками:
```cpp
#include <cstring>
#include <cassert>

char astr[] = "hello";
char bstr[15];
int alen = std::strlen(astr);
assert(alen == 5);

std::strcpy(bstr, astr);
std::strcat(bstr, ", world!");
res = std::strcmp(astr, bstr);
assert(res < 0);
foo(bstr);
```
А теперь работа с классом `string`:
```cpp
#include <string>

string astr = "hello";
string bstr;
int alen = astr.length();
assert(alen == 5);

bstr = astr;
bstr += ", world!";
res = astr.compare(bstr);
assert(res < 0);
foo(bstr.c_str());
```
Другой вопрос, почему это всё было не сделать внешними методами над `vector<char>` - тут, как я понимаю, дело в легаси соображения, короче просто так исторически сложилось.
### Шаблон класса строки
Представим на минуту (**это не так**), что строка была бы устроена вот так:
```cpp
template <typename CharT> class basic_string { .... };
```
И определения для удобства:
```cpp
using basic_string<char> string;
using basic_string<u16char_t> u16string;
using basic_string<u32char_t> u32string;
using basic_string<wchar_t> wstring;
```
Что бросается в глаза? Ответ - расширяемость.
Формально тогда можно сделать и безумное:
```cpp
using basic_string<float> fstring;
```
Нам будто хотелось бы предъявить некие критерии к типу, который образует строку... 
Подобное уже было - когда мы обсуждали итераторы - там характеристики разных типов итераторов хранились в `iterator traits`.
### Характеристики типов
Есть много вопросов, ответы на которые разные для разных строк с разными символами типов. Разумно свести всё это в класс:
```cpp
template <CharT> class char_traits;
```
Основные методы:
```cpp
assign, eq, lt, move, compare, find, eof ....

template <
	typename CharT,
	typename Traits = std::char_traits<CharT>
> class basic_string { .... }
```
Но это всё ещё не реальная строка. Есть ещё одна особенность - это работа с памятью для строк.

К слову, а является ли способ выделения памяти характеристикой символа?
Нет, это особенность всей строки, но тут у нас каждая строка особенная в контексте выделения памяти...

На помощь опять приходять характеристики типов - но теперь речь о типе с гарантиями по выделению определённой памяти - аллокаторы.
### Аллокаторы
Выделение памяти абстрагирует аллокатор. Стандартный аллокатор сводится к `malloc`.
```cpp
template <
	typename CharT,
	typename Traits = std::char_traits<CharT>,
	typename Allocator = std::allocator<CharT>
> class basic_string { .... };
```
К слову сказать, полный шаблон вектора тоже выглядит не совсем очевидно:
```cpp
template <
	typename T,
	typename Allocator = std::allocator<T>
> class vector { .... };
```
Важно понимать, что аллокатор не относится к аллокации настолько прямо, насколько может показаться, исходя из названия.

Аллокатор - это такой тип, который знает, **к кому надо обратиться**, чтобы уже тот объект выделял память в том или ином виде. 

Только это он и должен знать - куда сбегать, не более.

### Поиск в строках
Строки предполагают эффективные специальные возможности поиска в них
![[Pasted image 20260108094939.png]]
```cpp
string s = "Hello";

unsigned long notfound = s.find("bye");
// казалось бы, а откуда мы знает это тип??
assert(notfound == std::string::npos);

unsigned long ellp = s.find("ell");
unsigned long hpos = s.find("H", ellp);
assert(hpos == std::string::npos);
```
Кто видит возможную проблему в этом коде?
Оказывается, использование этих возможностей таит в себе сюрпризы:
![[Pasted image 20260108095427.png]]
```cpp
using szt = std::string::size_type;

string s = "Hello";

szt notfound = s.find("bye");
// казалось бы, а откуда мы знает это тип??
assert(notfound == std::string::npos);

szt ellp = s.find("ell");
szt hpos = s.find("H", ellp);
assert(hpos == std::string::npos);
```
Если не работать так со строками, могут возникать неочевидные проблемы.
Например, при портировании кода между платформами.
Секрет: 
- На `linux`:
  ```
  ull`size = 32 if 32-based and ull = 64 if 64-based
  
  the idea is to match the size of a pointer on system
  ```
- В вот на `windows`:
  ```
  ull = 32 in any case
  ```
