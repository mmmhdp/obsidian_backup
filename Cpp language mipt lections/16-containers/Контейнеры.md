# Последовательные контейнеры
**Контейнеры**:
- `vector` - есть гарантия по памяти.
массив с переменным размером и гарантией непрерывности памяти
- `array` - есть гарантия по памяти.
массив с фиксированным размером, известным в момент компиляции
- `deque`
массив с переменным размером без гарантий по памяти
- `list`
двусвязный список
- `forward_list`
односвязный список

**Адаптеры**:
- `stack`
FIFO контейнер, чаще всего на базе `deque`
- `queue`
LIFO контейнер, чаще всего на базе `deque`
- `priority_queue`
очередь с приоритетами, чаще всего на базе `vector`

## Что может смущать в этом коде?
```cpp
std::deque<int> d; // а если бы тут был вектор?

for (int i = 0; i != N; ++i)
{
	d.push_front(i);
// если вектор, то тут у операции O(n) сложность
	d.push_back(i);
// если вектор, то тут будут возникать потенциальные 
// реаллокации в неизвестном количестве
}

// Но использование deque лишает нас всех этих забот
// push_front() - O(1)
// гарантий по памяти нет - так что перевыделять не нужно
// т.е. push_back() - O(1), а не O(1+)
// поэтому тут всё хорошо
```
## Рассмотрите `deque` вместо `vector`
Про `deque`:
- Эффективно растёт в обоих направлениях
- Не требует больших реаллокаций с перемещениями, так как разбит на блоки
- Гораздо меньше фрагментирует кучу

## Деки против векторов

| Вектора                        | Деки                                       |
| ------------------------------ | ------------------------------------------ |
| Доступ к элементу за `O(1)`    | Доступ к элементу за `O(1)`                |
| Вставка в конец аморт. `O(1)+` | **Вставка в конец `O(1)`**                 |
| Вставка в начало `O(n)`        | **Вставка в начало `O(1)`**                |
| Вставка в середину `O(n)`      | Вставка в середину `O(n)`                  |
| Вычисление размера `O(1)`      | Вычисление размера `O(1)`                  |
| **Есть гарантии по памяти**    | Нет гарантий по памяти                     |
| Есть `reserve/capacity`        | **Нет необходимости в `reserve/capacity`** |
Но интересно, что на практике замеры показывают, что на самом деле доступ к элементу у деки примерно на `30%` медленне, чем у вектора, та самая константа прилично больше у деки.
## Обсуждение

- "`deque is the data structure of choice then most insertions and deletions take place at the beginning or at the end of the sequence`"
Как бы вы его реализовали?

упрощены для такой структуры до `O(1)`. Т.е. всё необходимое на месте.

## Особая возвожность списков: итераторы
У списков никогда не инвалидируются итераторы после операций, что позволяет найти для них применение, когда нам важно сохранить итераторы и использовать их в дальнейшем.

Пример - `lru-cache`, иначе, как списком там не воспользоваться, так как в итоге нам необходимо хранить указатели на элементы, это то что мы делаем в `C`, а сейчас мы будем хранить вместо них итераторы на один из видов списка и получать такой же результат.
## Особая возвожность списков: `splice`
![[Pasted image 20260106113041.png]]
### Сплайс для списков: простая форма
Сложность `O(1)`
```cpp
forward_list<int> fst = {1, 2, 3};
forward_list<int> snd = {10, 20, 30};
auto it = fst.begin(); // указывает на 1

// перемещение second в начало first, it указывает на 1
fst.splice_after(fst.before_begin(), snd);
```
![[Pasted image 20260107103636.png]]
### Сплайс для списков: сложная форма
Сложность `O(n)`
```cpp
forward_list<int> fst = {10, 20, 30 ,1, 2, 3};
forward_list<int> snd = {};

// it всё ещё указывает на 1

// перекидываем элементы со второго по it в список second
snd.splice_after(snd.before_begin(), fst, fst.begin(), it);
```
![[Pasted image 20260107104000.png]]
### Сплайс для списков: средняя форма
Сложность `O(1)`
```cpp
forward_list<int> fst = {10,,1, 2, 3};
forward_list<int> snd = { 20, 30 };
// it всё ещё указывает на 1

// все элементы второго списка начиная со второго в первый
fst.splice_after(fst.before_begin(), snd, snd.begin());
```

### Виды адаптеров
Казалось бы, оба эти контейнера реализуются на `deque`, но у них есть особенности, которые выделяют их - например, `stack` как адаптер по умолчанию действительно использует `deque` как базовый контейнер, но на самом деле `stack` может быть обёрткой для любого контейнера с определённым интерфейсом. Тоже относится и к другим адаптерам.

Идея в том, что мы явно указываем то, что в данной ситуации контейнер должен иметь лишь урезанный до адаптера интерфейс.
- `stack` - `LIFO` стек над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = deque<T>
> class stack;
```
- `queue` - `FIFO` очередь над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = deque<T>
> class queue;
```
- `priority_queue` - очередь с приоритетами (как `binary heap`) над последовательным контейнером
```cpp
template <
	typename T, 
	typename Container = vector<T>,
	typename Compare = less<typename Container::value_type>
> class priority_queue;
```
### Защита от ортогональности
```cpp
std::stack<int> s; // ок, это stack <int, deque<int>>
std::stack<int, std::vector<long>> s1; // сомнительно
std::stack<int, std::vector<char>> s2; // совсем плохо 

s2.push(1000);
// а что тогда вернёт s2.top()?
```
К счастью, подобное безобразите покрыто `static_assert`'ами
### Недостаточная ортогональность
```cpp
std::stack<int, std::forward_list<int>> s; // ок

s.push(100); // ошибка: нет push_back
s.pop(); // ошибка: нет pop_back
s.top(); // ошибка: нет back
```
Эти ошибки не очевидны, стек то вполне может быть сделан на односвязном списке. Но дело в том, что адаптер `stack` требует (неявно) вполне определённый интерфейс от внутреннего контейнера.
## Обсуждение
- Почему `stack`,`queue` и `priority_queue` не являются отдельными контейнерами?
Плюсы смены контейнера идут от особенностей контейнера. Например, если мы уверены, что размер стека будет меняться нечасто и малыми шагами, а также хотим увеличить локальность кэша - то положить вектор место деки в основу - хорошая идея.
- И почему тогда двухголовая очередь - `deque`, не является адаптером? 
Ответ от лектора - кажется, что корневое отличие адаптера от контейнера состоит в том, как контейнеры работают с памятью, именно в этом разница - у каждого контейнера свой специфичный подход к организации памяти.
# Контейнеро-подобные классы
Конкретные классы которые удобно использовать для конкретных задач.
## `bitset`
`bitset` - это альтернатива `array<bool>` то есть у него фиксированный размер, являющийся параметром контейнера.
При этом, он хранит данные более компактно (как `vector<bool>`)
```cpp
// 24-bit number
bitset<24> s1 = 0x7ff000;
bitset<24> s2 = 0x00ff00;

s1[0] = 1; // или s1.set(0) или s1.set(0, 1)

auto s3 = s1 & s2; // s3 = 0xf000
```
По сути он делает `array<bool>` (который не оптимизирует хранение, а честно хранит каждое значение в отдельном `char`'е) не нужным.
## `string`
### Обсуждение: поговорим о строках

- Почему специальный `std::string`(конечно, это алиас, тут должен быть `std::basic_string<char>`) а не `vector<char>`?
  *Важная ремарка*: формально `std::string` это непрерывный контейнер, имеющий с вектором много общего.
Ответ банальный - строки специфичны, а значит, нам бы хотелось иметь особый, привязанный к строкам интерфейс для работы с ними.
### Строки: базовая функциональность
Сравним со старым добрым `C-style` работой со строками:
```cpp
#include <cstring>
#include <cassert>

char astr[] = "hello";
char bstr[15];
int alen = std::strlen(astr);
assert(alen == 5);

std::strcpy(bstr, astr);
std::strcat(bstr, ", world!");
res = std::strcmp(astr, bstr);
assert(res < 0);
foo(bstr);
```
А теперь работа с классом `string`:
```cpp
#include <string>

string astr = "hello";
string bstr;
int alen = astr.length();
assert(alen == 5);

bstr = astr;
bstr += ", world!";
res = astr.compare(bstr);
assert(res < 0);
foo(bstr.c_str());
```
Другой вопрос, почему это всё было не сделать внешними методами над `vector<char>` - тут, как я понимаю, дело в легаси соображениях, короче просто так исторически сложилось.
### Шаблон класса строки
Представим на минуту (**это не так**), что строка была бы устроена вот так:
```cpp
template <typename CharT> class basic_string { .... };
```
И определения для удобства:
```cpp
using basic_string<char> string;
using basic_string<u16char_t> u16string;
using basic_string<u32char_t> u32string;
using basic_string<wchar_t> wstring;
```
Что бросается в глаза? Ответ - расширяемость.
Формально тогда можно сделать и безумное:
```cpp
using basic_string<float> fstring;
```
Нам будто хотелось бы предъявить некие критерии к типу, который образует строку... 
Подобное уже было - когда мы обсуждали итераторы - там характеристики разных типов итераторов хранились в `iterator traits`.
### Характеристики типов
Есть много вопросов, ответы на которые разные для разных строк с разными символами типов. Разумно свести всё это в класс:
```cpp
template <CharT> class char_traits;
```
Основные методы:
```cpp
assign, eq, lt, move, compare, find, eof ....

template <
	typename CharT,
	typename Traits = std::char_traits<CharT>
> class basic_string { .... }
```
Но это всё ещё не реальная строка. Есть ещё одна особенность - это работа с памятью для строк.

К слову, а является ли способ выделения памяти характеристикой символа?
Нет, это особенность всей строки, но тут у нас каждая строка особенная в контексте выделения памяти...

На помощь опять приходять характеристики типов - но теперь речь о типе с гарантиями по выделению определённой памяти - **аллокаторы**.
### Аллокаторы
Выделение памяти абстрагирует аллокатор. Стандартный аллокатор сводится к `malloc`.
```cpp
template <
	typename CharT,
	typename Traits = std::char_traits<CharT>,
	typename Allocator = std::allocator<CharT>
> class basic_string { .... };
```
К слову сказать, полный шаблон вектора тоже выглядит не совсем очевидно:
```cpp
template <
	typename T,
	typename Allocator = std::allocator<T>
> class vector { .... };
```
Важно понимать, что аллокатор не относится к аллокации настолько прямо, насколько может показаться, исходя из названия.

Аллокатор - это такой тип, который знает, **к кому надо обратиться**, чтобы уже тот объект выделял память в том или ином виде. 

Только это он и должен знать - куда сбегать, не более.

### Решение: `string_view` (C++17)
`string_view` - это невладеющий указатель на строку.
```cpp
static std::string_view kName = "oh literal, my literal";

// some code
int foo(std::string_view arg);

// more code
foo(kName);
```
Здесь нет ни `heap indirection`, ни создания временного объекта.

Важно понимать, что `string_view` инкапсулирует указатель на строку и размер, но не владеет объектом. Т.е. фактически, он спокойной может провиснуть, т.е. это именно что `view` на некоторый объект, в данном случае строку.
#### Базовые операции над `string_view`
- `remove_prefix`
- `remove_suffix`
- `copy`
- `substr`
- `compare`
- `find`
- `data`
```cpp
std::string str = "  trim me  ";
std::string_view sv = str;

auto trimfst = sv.find_first_not_of(" ");
auto minsz = std::min(trimfst, sv.size());

sv.remove_prefix(minsz);

auto trimlst = sv.find_last_not_of(" ");
auto sz = sv.size() - 1;
minsz = std::min(trimlst, sz);

sv.remove_suffix(sz - minsz);
```
### `Views`: идея для `span`(C++20)
`std::span` для одномерных массивов то же, что `string_view` для строк:
```cpp
int arr[4] = {1, 2, 3, 4}; 
// просто данные 
std::array<int, 4> arr = {1, 2, 3, 4}; 
// копирование до main
```
`span` решает эту проблему:
```cpp
std::span<int, 4> arr = {1, 2, 3, 4}; // просто данные
```
По умолчанию второй параметр `N` это `std::dynamic_extent`:
```cpp
std::span<int> dynarr(arr); // неизвестный размер
```
Разумеется, у `span` куда более простой интерфейс, чем у `string_view`.

# Ассоциативные контейнеры
## Смысл ассоциативности
Вектора индексированы целыми числами и позволяют сопоставить целое число хранимому значению:
```cpp
vector<T> v; // int -> T
```
Т.е. реализуется отображение из целого числа в тип.

Референс: ранее, на примере `integral_value` ([[Вектора и SFINAE#Интегральные константы]]) уже показана возможность построить отображение из чисел на типы.

А как выразить произвольное отображение из типов в типы (`T -> U`)?

Идея номер раз: `T -> U : (T -> int) -> U : int -> U`
Т.е. сделать из любого типа что-то в роде инта, а дальше мы уже умеем.

`T -> int` - а вот такое, в общем случае, и проделывает хеширование.
## Ассоциативный массив
Основная идея ассоциативного массива - это контейнер `undordered_map`
```cpp
template <
	typename Key, typename T,
	typename Hash = std::hash<Key>,
	typename KeyEqual = std::equal_to<Key>,
typename Allocator = std::allocator<std::pair<const Key, T>>
> class unordered_map;
```
Здесь важными являются два отношения:
- отношение `equals`
- и собственно `hash`- функция.

При этом ключи уникальны и мы можем менять значение, но не ключи.
### Обсуждение: собственный ключ
Допустим, у нас есть пользовательская структура из двух строк:
```cpp
struct S {
	std::string first_name, last_name;
};

std::unordered_map<S, std::string> Ump; // error
```
Для неё нужно сделать две вещи:
- Определить равенство (`spaceship operator`). Достаточно?
- Определить хеш. А как бы это сделать хорошо?

Обратите внимание: мы можем добавлять в библиотеку специализации для наших классов, но мы не можем добавлять перегрузки для функций в пространство имён `std`.
#### Собственный hash
##### DIY
Простейший способ сделать что-нибудь исходя из фантазии:
```cpp
size_t operator()(const S& s) const noexcept {
	std::hash<std::string> h;
	auto h1 = h(s.first_name), h2 = h(s.last_name):
	return h1 ^ (h2 << 1);
};
```
Этот способ кажется привлекательным, так как мы же программисты.
Часто (например в этом случае) это даже работает.
НО в общем и целом это всегда угадайка.
##### Опыт предков
Если угадайка не особо привлекает, то есть `boost`:
```cpp
size_t operator()(const S& s) const noexcept {
	std::hash<std::string> h;
	auto h1 = h(s.first_name), h2 = h(s.last_name):
	size_t seed = 0;
	boost::hash_combine(seed, h1);
	boost::hash_combine(seed, h2);
	return seed;
};
```
Это работает всегда и имеет качественные математические свойства, но для этого надо затаскивать `boost` в проект.
#### Обсуждение: равенство
Есть подозрение, что то, как мы подошли к реализации равенства для нашей структуры, идея на самом деле более глубокая, чем кажется на первый взгляд. Рассмотрим саму концепцию равенства подробнее.
Оказывается, равенство формулируется в терминах сравнение `на меньше`.
##### Требования к предикату сравнения
Общая концепция называется `strict weak ordering`.
Она включает в себя:
- Антисимметричность: $\mathrm{pred}(x, y) \Rightarrow \neg \mathrm{pred}(y, x)$
- Транзитивность: $\mathrm{pred}(x, y) \land \mathrm{pred}(y, z) \Rightarrow \mathrm{pred}(x, z)$
- Иррефлексивность: $\neg \mathrm{pred}(x, x)$
- Транзитивность эквивалентности: 
  $\mathrm{eq}(x, y) \equiv \neg \mathrm{pred}(x, y) \land \neg \mathrm{pred}(y, x) \vdash \mathrm{eq}(x, y) \land \mathrm{eq}(y, z) \Rightarrow \mathrm{eq}(x, z)$

Она же распространяется на предикаты в алгоритмах сортировки и т.д.

## Низкоуровневая информация
Дополнительно каждый неупорядоченный контейнер даёт возможность смотреть его статистику:
- `bucket_count()` - кол-во бакетов
- `max_bucket_count()` - максимальное количество бакетов без реаллокации
- `bucket_size(n)` - размер бакета с номером `n` 
- `bucket(Key)` - номер бакета для ключа `Key`
- `load_factor()` - среднее количество ключей в бакете
- `max_load_factor()` - максимальное количество ключей в бакете
## Обсуждение
По сути, неупорядоченный контейнер это что-то вроде гибрида непрерывного и узлового последовательного контейнера.
Что это означает в контексте управления памятью?

Напоминание: в узловых контейнерах (`list`) управлять памятью не нужно кроме случаев особых аллокаторов. А в последовательных (`vector`) об этом забывать нельзя.

В этом смысле `unordered_map` ближе к `vector`.
## `Rehash`
Особая функция `rehash(count)` служит для того, чтобы изменить количество бакетов (установить в `count`) и перераспределить между ними элементы:
`reserve(count)` 
делает тоже самое, что и 
`rehash( ceil(count / max_load_factor()) )'

Особый случай `rehash(0)` позволяет безусловно (в автоматическом режиме) перехешировать контейнер.

## Два вида итерации
По хеш-таблице можно итерировать как по единому массиву:
```cpp
for (auto it = m.begin(), end = m.end(); it != end; ++it){ 
 .... 
}
```
Можно итерироваться внутри бакета, указав его номер:
```cpp
for (int i = 0; i < m.bucket_count(); ++i){
	for (auto it = m.begin(i), end = m.end(i);
		it != end; ++it){
		....
	}
} 
```
В обоих случаях вам доступен только `forward` итератор.
Как бы вы написали адаптор чтобы позволить второй вариант через `range-based for`?
Ответ: сделать структуру и в ней уже прокинуть связь `begin -> begin(i)` и итерироваться уже по ней:
```cpp
#include <iostream>
#include <unordered_map>

template <typename K, typename V = K> struct BucketForEachAdapter {
  std::unordered_map<K, V> &m_;
  int bucket_idx_ = 0;

  auto begin() { return m_.begin(bucket_idx_); }

  auto end() { return m_.end(bucket_idx_); }
};

int main() {
  std::unordered_map<int, int> m;

  for (auto i = 0; i < 10; ++i)
    m[i] = i;

  for (int i = 0; i < m.bucket_count(); ++i) {
    std::cout << "Bucket with index:" << i << std::endl;
#if 0
    for (auto it = m.begin(i), end = m.end(i); it != end; ++it) {
      std::cout << it->first << " " << it->second << std::endl;
    }
#endif

    for (auto &&it : BucketForEachAdapter<int, int>{m, i}) {
      std::cout << it.first << " " << it.second << std::endl;
    }
  }
}
```

# Упорядоченные контейнеры
## Уникальность элементов
Упорядоченное множество также хранит упорядоченные элементы:
```cpp
std::set<int> s = {67, 42, 141, 23, 42, 106, 15, 50};

for (auto elts : s) std::cout << elt << std::endl;
```
Ничего не сломается но на экране будет: 
```cpp
15, 23, 42, 50, 106, 141
```
Главное отличие от `unordered_set`: оно хранит их именно что упорядоченно.
Это позволяет `range-based queries` через `upper` и `lower bound`.
## Порядок сравнения
Множество создаёт упорядочение своих элементов:
```cpp
std::set<int> s = {67, 42, 141, 23, 42, 106, 15, 50};

auto itb = s.lower_bound(30);
auto ite = s.upper_bound(100);
```
Теперь можно итерировать в интервале `[30, 100)` не зависимо от того, есть ли в множестве в точности такие элементы:
```cpp
for (auto it = itb; it != ite; ++it)
	std::cout << *it << std::endl;
```
На экране:
```cpp
42, 50, 67
```

Также можно задать любой предикат упорядочения:
```cpp
std::set<int, std::greater<int>> s = {
	67, 42, 141, 23, 42, 106, 15, 50
};

auto itb = s.lower_bound(30);
auto ite = s.upper_bound(100);
// вот тут с такими компаратором возникнет 
// невалидный диапазон [itb -> ite)
```
Задают ли итераторы `itb` и `ite` валидный интервал для итерирования?
Т.е. нет, не задают.

Что будет, например, в таком цикле?
```cpp
for (auto it = itb; it != ite; ++it)
	std::cout << *it << std::endl;
```
Ответ - всё, что угодно - итерация по невалидному диапазону - это `UB`.
```cpp
std::set<int, std::greater<int>> s = {
	67, 42, 141, 23, 42, 106, 15, 50
};

auto itb = s.lower_bound(100);
auto ite = s.upper_bound(30);
// теперь диапазон валиден

for (auto it = itb; it != ite; ++it)
	std::cout << *it << std::endl;
	
// теперь это работает, но само собой
// конструкция в крайней мере контринтуитивна
```

А что если теперь мы выберем упорядочить по (`<=`):
```cpp
std::set<int, std::less_equal<int>> s = {
	67, 42, 141, 23, 42, 106, 15, 50
};

auto itb = s.lower_bound(30);
auto ite = s.upper_bound(100);
```

Валиден ли в таком случае диапазон?
```cpp
for (auto it = itb; it != ite; ++it)
	std::cout << *it << std::endl;
```
Этот компаратор меняет понятие равенства двух элементов, что влёчёт за собой разрушение инвариантов контейнера, что в свою очередь делает предсказание последствий такого подхода слабо предсказуемыми.

Более того, в данном случае это просто `UB`.

Свойства сравнения - это семантическая характеристика, поэтому этот код будет компилироваться, но вот работать корректно - уже нет.

## Обсуждение: `multiset` и предикат
Наверное, в `multiset`, где возможны одинаковые элементы, такие же требование к предикату сравнения (а они там тоже действуют) введены зря?
Может быть они там не нужны?

Нет, они там не зря. Майерс сделал интересное наблюдение:
```cpp
std::multiset<int, std::less_equal<int>> s;

s.insert(10); // insert 10_a
s.insert(10); // insert 10_b
```
А теперь `equal_range` для `10` вернёт пустой интервал (ведь при поиске мы будет искать наличие некого объекта `10_c`, который очевидно не равен ни `10_a`, ни `10_b`) , что, очевидно, абсурдно.

**Общий итоговый вывод**: `strict weak ordering` это очень важная концепция.
## Обсуждение: удаление
Контейнер `std::map` упорядочен по ключам, но не по значениям.

Предположим, мы хотим удалить из отображения все пары ключ-значение в неком диапазоне значений.

Мы врядли сможем сделать нечто лучше, чем нечто вроде:
```cpp
for (auto it = s.begin(), end = s.end(); it != end; ++it)
	if (it.second < max && it.second > min)
		s.erase(it);
```
Что тут не так?
Есть ощущение, что после первого же `s.erase(it)` итераторы инвалидируются, а после этого уже ничего не важно, это `UB`.

Угадал:
`References and iterators to the erased elements are invalidated. Other references and iterators are not affected.`
Т.е. после `erase()` у нас уже инвалидирован `it`, а далее мы его инкрементируем, т.е. летим в `UB`.

Это одна из тех редких операций в упорядоченных контейнерах, что инвалидирует итераторы. Но даже тут, не все.
Это даёт возможность найти решение проблемы.
## Не стреляйте себе в ногу через `erase`
Плохая идея:
```cpp
for (auto it = s.begin(), end = s.end(); it != end; ++it)
	if (it.second < max && it.second > min)
		s.erase(it); // тут итератор стал невалидным
```
В рамках `C++98` вопрос решался так:
```cpp
for (auto it = s.begin(), end = s.end(); it != end;)
	if (it.second < max && it.second > min)
		s.erase(it++); // и это и правда работает
	else:
		++it;
```
В рамках `C++11` сделали так:
`Return value: [1-3) Iterator following the last removed element.`
```cpp
for (auto it = s.begin(), end = s.end(); it != end;)
	if (it.second < max && it.second > min)
		it = s.erase(it); 
	else:
		++it;
```
## Обсуждение: замена элемента
Предложите решение для замены элемента в множестве:
```cpp
auto it = s.find(1);
if (it != s.end()) 
	*it = 3; // error: assigment of read-only location
```
Допустим, вам таки необходимо заменить `1`на`3`. Что делать тогда?

Но теперь нам очевидно решение - удалить, а потом вставить:
```cpp
auto it = s.find(1);

if (it != end()){
	s.erase(it); s.insert(3);
}
```
Удалить, а потом вставить в случае узловых контейнеров - это часто дёшево, поэтому не стоит бояться так делать.
