# Простые прикладные итераторы
## Первый пример: обход вектора
Задача: пока функция `func` возвращает `true` применять её к элементам вектора
```cpp
template <typename F>
size_t traverse(vector<int>& v, F func)
{
	size_t nelts = v.size();
	for (size_t i = 0; i != nelts; ++i)
	{
		if (!func(v[i]))	
			return i;
	}
	return nelts;
}
```
### Обобщение обхода
`vector<int>` в аргументе, но тут вообще говоря нет специфичного именно для этого контейнера с этим типом когда, т.е. можно обобщить код:
```cpp
template <typename Cont, typename F>
size_t traverse(Cont& cont, F func)
{
	size_t nelts = cont.size();
	for (size_t i = 0; i != nelts; ++i)
	{
		if (!func(cont[i]))	
			return i;
	}
	return nelts;
}
```
Но кажется, нам тут совсем не нужен `random access` к элементам контейнера, мы скорее хотим просто пройти по всем элементам, тогда:
```cpp
template <typename Cont, typename F>
size_t traverse(Cont& cont, F func)
{
	size_t elts = 0;
	for (auto it = cont.begin(), end = cont.end();
		it != end; ++it, ++elts;) 
	{
		if (!func(*it))	
			break;
	}
	
	return elts;
}
```
А теперь сюда зайдёт любой контейнер.
Но можно ещё продвинуться, используя `range-based` обход.
### `Range-based` обход
Нам на самом деле не нужны итераторы тут, нам необходим только элемент для обработки, а значит:
```cpp
template <typename Cont, typename F>
size_t traverse(Cont& cont, F func)
{
	size_t elts = 0;
	for(auto &&el: cont) {
		if (!(func(el)) // el это *it
			break;
		++elts;
	}
	
	return elts;
}
```
Тут уже очевидны две ответственности этого цикла.
Как в стандарте описан `range-based for`:
```cpp
for (range_declaration : range_expression) 
	loop_statement;
	
	
// в C++20 доступна ещё форма:
for (init_-statement; range_declaration : range_expression) 
	loop_statement;

```
Эквивалентно это всё следующему:
```cpp
auto &&__range = range_expression;
auto __begin = begin(__range);
auto __end = end(__range);

for(;__ begin!=__end; ++__begin) {
	range_declaration = *__begin;
	loop_satement;
}
```
### Требования к `range-based` обходу
Объект, возвращаемый `begin()`должен поддерживать:
- Инкремент
- Разыменование
- Сравнение на неравенство

```cpp
for(;__ begin!=__end; ++__begin) {
	range_declaration = *__begin;
```
Эти требование входят в статический интерфейс (`concept`) прямого итератора. Можно заметить, что всем этим требованиям удовлетворяют обычные указатели.
**Важно**: итератор - это не какой-то конкретный класс и не наследник какого-то класса, это что угодно с описанным выше интерфейсом.

Но важно также понимать, что итераторы, хоть и имеют статический интерфейс более скудный, чем просто указатели, на самом деле умеют чуть больше, чем было сказано. Рассмотрим разные типы итераторов на этом фоне, сравним с тем, что они могут на фоне указателей.
# Виды итераторов
### Свойства указателей
- Создание по умолчанию, копирование, копирующее присваивание
- Разыменование как `rvalue` и доступ к полям по разыменованию
- Разыменование как `lvalue` и присваивание значения элементу под ними
- Инкремент и постинкремент за `O(1)`
- Сравнимость на равенство и неравенство за `O(1)`
- Декремент и постдекремент за `O(1)`
- Индексирование квадратными скобками, сложение с целыми, сравнение на больше и меньше за `O(1)`
- Многократный проход по одной и той же последовательности

## Итераторы: дело в асимптотике
- Инкремент и постинкремент за `O(1)` - `forward`
- Сложение с целыми за `O(1)` - `random-access`
- Довольно очевидно, что для `forward` итератора в общем случае продвижение на произвольное расстояние это `O(N)`

Есть функции, которые прячут это под капотом, на них уже не наложены те требования по амортизации, что существуют для итераторов, а значит, данные функции позволят подсветить в коде, что данный обход может иметь высокую асимптотическую сложность, по крайней мере, она может быть выше того, что требуется от итератора в стандарте:
```cpp
std::distance(Iter fst, Iter snd);
// snd - fst, либо же подсчёт через цикл

std::advance(Iter fst, int n);
// fst + n, либо опять же через цикл

/*
	Делают они это устраивая явную перегрузку 
	по тегу категории итератора
*/
```
## Обсуждение
Продолжим работу над функцией `traverse`.

Учитывая возможную плохую асимптотику `distance`, это код может быть чуть хуже явного цикла:
```cpp
template <typename C, typename F>
size_t traverse(C&& cont, F func){
	auto it = std::find_if_not(
		cont.begin(), cont.end(), func);
	return std::distance(cont.begin(), it);
}
```
Но может быть он чем-то лучше?
## Обсуждение: используйте итераторы
Этот пример лучше тем, что он явно указывает на реальные требования, 
которые предъявляет функция `traverse` - ей на самом деле не нужен контейнер, хватает двух итераторов на начало и конец контейнера. Подобное возникает часто:
```cpp
template <typename It, typename F>
size_t traverse(It start, It fin, F func){
	auto it = std::find_if_not(start, fin, func);
	return std::distance(start, it);
}
```
А есть ли разница по скорости при применении такого подхода?
Ответ - да, и она может быть огромной, в пользу использования двух итераторов.

А причина простая - уровни косвенности. Передавая итераторы сразу, мы убираем уровень косвенности, что и даёт иногда критический прирост в производительности в зависимости от задачи.

Именно поэтому все алгоритмы стандартной библиотеки так или иначе берут именно итераторы в оборот.
# Категории итераторов
## Определение категории итераторов
Ранее мы уже обозначили, что `input` и `output` итераторы отличаются только в семантическом, но не синтаксическом смысле. 

Такая ситуация, когда мы хотим семантические различия вынести на уровень синтаксиса, удобно использовать теги - это некий набор пустых классов со своей иерархией, от которых уже наследуется класс, который реализует тот или иной семантический интерфейс.

Используется для этого класс характеристик:
```cpp
typename iterator_traits<Iter>::iterator_category
```
Возможные значения:
```cpp
input_iterator_tag

output_iterator_tag

forward_iterator_tag : public input_iterator_tag

bidirectional_iterator_tag : public forward_iterator_tag

random_access_iterator_tag: public 
	bidirectional_iterator_tag
/*
 а также их наследники 
 а также любые другие иерархии, которые могут быть заданы
 пользователем языка 
 
 тут ООП начинает искрить, когда мы используем возможности 
 классов для работы с шаблонами, как и говорил выше
 мы затыкаем дыры, переводя семантику в представление 
 в коде, а фактически, с точки зрения ООП мы делаем 
 чудовищные вещи - 
 например, в input_iterator_tag нет виртуального 
 деструктора, хотя в этом классе нет методов и состояния,
 т.е. он абстрактный в какой-то мере, но мы просто оставляем
 его пустым, так как мы надеемся на то, что никому в
 голову не придёт удалять условный forward_iterator_tag 
 по указателю на его базу.
*/ 
```
Важно уточнить, что для того, чтобы ваш итератор можно было распознать,
можно пойти двумя путями:
- Положиться на `SFINAE` и иметь в своём итераторе поле `Iter::iterator_category`, который и будет взят в рассмотрение в качестве тега для дальнейшей работы, т.е. тогда наш тип будет одним из типов, который будет валиден для `iterator_traits<Iter>`.
```cpp
class MyIter {
	iterator_category = std::input_iterator_tag;
	....
	/*
		на самом деле итераторы требуют ещё набор
		некоторой метаинформации для полноценной работы,
		но это тут не так важно
	*/
	....
};
```
- А можно специализировать `iterator_traits` вашим типом итератора, что является валидным действием над пространством имён стандартной библиотеки:
```cpp
/* 
 в таком случае сам класс итератора будет содержать в
 себе меньше информации, но это и нормально,
 так как обращения к этой информации, например,
 о типе итератора, происходит именно что через 
 iterator_traits:
 
 using category = typename 
	iterator_traits<Iter>::iterator_category
	
 а значит, таскать это всё в классе или нет - 
 вопрос может и философский, но с перекосом
*/
namespace std {
	template <>
	struct iterator_traits<MyIter> {
		iterator_category = std::input_iterator_tag;
		....
	};
}
```
Важно - когда мы задумываемся над написанием своего итератора, мы в первую очередь как раз и определяемся с его тегом, с его категорией, так как без принадлежности к категории мы не можем чётко указать, а какой семантический контракт мы сейчас будем реализовавать.

Далее мы правда ещё обсудим этот вопрос, возможно, есть ещё более важные вещи)

Например, перегрузим вывод для тегов чтобы отлаживать наши программы:

```cpp
ostream& operator<<(ostream& out,

	out << "random_access";
```

### Проверка категории
Иногда мы хотим обложить перегрузку `SFINAE` проверкой:
```cpp
template <typename It>
// имеет смысл только для input iterators
void foo(It fst, It lst){....}
```
Может ли тут нам помочь уже известный приём с `void_t`([[Вектора и SFINAE#void_t]])? 
Кажется, что только с `void_t` нам успеха не добиться, всё же он может ответь на вопрос существования, но вот организовать `substitution failure` при выполнении некого условия он прям с ходу не может.
#### Интерлюдия: `conditional_type`
Рассмотрим следующую `sfinae-триаду`:
```cpp
template <bool B, typename T, typename F>
struct conditional { using type = T;}

template <typename T, typename F>
struct conditional<false, T, F> { using type = F;}

template <bool B, typename T, typename F>
using conditional_t = typename conditional<B,T,F>::type;
```
Она представляет собой условный тип.
А можно ли его сделать невалидным для `F`?
Да, просто вычеркнем технически все упоминания `false-type`:
```cpp
template <bool B, typename T /*, typename F */>
struct conditional { using type = T;}

template <typename T /*, typename F */>
struct conditional<false, T /*, F */> { /*using type = F;*/}

template <bool B, typename T /*, typename F */>
using conditional_t = typename 
	conditional<B, T/*,F */>::type;
```
Тогда при `false` подстановка провалится, так как там просто не будет поля `type`, чего мы и хотели добиться.

Но что если пойти дальше и отказаться и от типа `T` как необходимого?
У нас ведь есть валидный тип по умолчанию - `void`. Эта дорога приводит нас к `enable_if`.
### `ENABLE_IF`
Получившаяся триада `enable_if` является одной из самых полезных идиом в практическом `SFINAE`:
```cpp
template <bool B, typename T = void>
struct enable_if { using type = T;}

template <typename T = void>
struct enable_if<false, T > { }

template <bool B, typename T = void>
using enable_if_t = typename enable_if<B, T>::type;
```
Т.е. если `void_t` - это "И", то `enable_if` это, как не странно, "if".
### Проверка категории с `enable_if`
```cpp
template <typename It>
using iterator_category_t = 
	typename std::iterator_traits<It>::iterator_category;

template <
	typename It,
	typename T = std::enable_if_t<
		std::is_base_of_v<
		// _v - вернёт значение
		// а вообще задача проверить
		// является ли это
			input_iterator_tag,
		// базовым классом для этого
			iterator_category_t<It>
		>		
	// второй аргумент тут void, 
	// мы тут просто хотим проверить условие
	>
> void foo(It fst, It lst) {....}
// в итоге мы получаем успешную подстановку только
// при условии вызова для input iterator`a 
```
## Обсуждение
Вернёмся к вопросу про итераторы и их написание.
Ранее уже было сказано о том, что написание итератора стоит начинать с 
определения его категории. Реальность же такова, что кроме категории, для полноценной работы с функциями стандартной библиотеки для итераторов, которые мы тоже обсуждали (`std::distance` например), нам необходимо снабдить итератор дополнительными метаданными о свойствах данного итератора. class Iter {
```cpp
	....

	using iterator_category = 
		std::bidirectional_iterator_tag;
	using value_type = int;
	using difference_type = ptrdiff_t;
	using pointer = int*;	
	using reference = int&;
};
```
## `Case study`: пишем свой итератор

```cpp
std::vector<double> values = {4.0, 3.0, 2.0, 1.0};
```

### Пишем свой итератор: первые шаги
В нашем итераторе, как мы ранее заметили, нам необходимо определить пять фундаментальных подтипов, рекомендуется такая последовательность - от простого к сложному:
1. `iterator_category`- категория итератора
2. `difference_type`- тип для хранения разности итераторов
3. `value_type`- тип значений, по которым мы итерируемся
4. `reference`- тип ссылки на значения, по которым мы итерируемся
5. `pointer`- тип указателя на значения, по которым мы итерируемся
### Простые вещи
Некоторые вещи действительно просты:
```cpp
// вспомогательные using для value_type составных частей
using KeyType = typename
	iterator_traits<KIter>::value_type;
using ValueType = typename
	iterator_traits<VIter>::value_type;
	
// наше же value - это пара values
using value_type = std::pair<KeyType, ValueType>
```
К сожалению, так нельзя определить тип `pointer`, так как на **самом деле**
мы не итерируемся по контейнеру пар. Мы вернёмся к этому вопросу чуть позже. Вернуть `pointer` в качестве указателя на пару из указателей - `dead parrot`, он провиснет, это будет указатель на временный объект, нужен другой подход.
### Базовый интерфейс
Никаких проблем, чтобы попарно уменьшать и увеличивать итераторы:
```cpp
zip_iterator_t(KeyIt Kit, VIt Vit) : Kit_(Kit), Vit_(Vit){}
zip_iterator_t& operator++(){ ++Kit_; ++Vit_; return *this;}
zip_iterator_t& operator++(int){
	// тоже ничего сложного
}
```
Первая засада ждёт на операторе разыменования:
```cpp
using reference = std::pair<KeyType&, ValueType&>;
reference operator*() const {return {*Kit_, *Vit_}; }
```
### Всегда пользуйтесь `traits`
Очевидно:
```cpp
using reference = std::pair<KeyType&, ValueType&>;
```
Это ошибка, если в контейнере `reference` отличается от `value&`, например для `vector<bool>` и многих других.

Корректно:
```cpp
using KeyRef = typename
	std::iterator_traits<KeyIt>::reference;
using ValueRef = typename 
	std::iterator_traits<ValueIt>::reference;

using reference = std::pair<KeyRef, ValueRef>;
reference operator*() const {return {*Kit_, *Vit_}; } // ok
```
### Настоящая проблема: стрелочка
Как вообще должен выглядеть оператор разыменования?
```cpp
auto zit = make_zip_iterator(k.begin(), b.begin());
assert (k.front() == zit->first);

// zit->first drills down to (zit.operator->())->first
```
Это должен быть аналог разыменованию и обращению к полю:
```cpp
pointer operator->() const { return /*some pointer*/;}
```
Но что такое `pointer`? Просто решение не подходит:
```cpp
using pointer = std::pair<KeyPtr, ValuePtr>;// нет p->first
```

Первый всегда доступный вариант - указать на то, что такой стрелки и не должно быть:
```cpp
using pointer = void;
// тогда компилятор будет тоже в курсе, что стрелки нет
```
Второй - думать...
#### Некоторые дурацкие варианты
Можно продлить временному объекту жизнь, сделав его статическим:
```cpp
using pointer = value_type*;

pointer operator->() const {
	static reference Ref;
	Ref = {*Kit_, *Vit_};
	return &Ref;
}

// пример того, когда это стреляет в ногу
use(zit->first, (zit + 1)->first); 
```
#### Изящное решение: прокси класс
На помощь приходит прокси-класс:
```cpp
template <typename Reference> 
struct arrow_proxy {
	Reference R;
	Reference *operator->() {return &R;} // non const
};

using pointer = arrow_proxy<Reference>;

pointer operator->() const {
	return pointer{{*Kit_, *Vit_}};
}
```
Есть некоторые опасения в том, что прокси провиснет, но нам он нужен чтобы пережить `drill-down`, а его явно переживёт.

Первым такую диаграмму нарисовал Майерс:

Но он обнаружил, что эта даграмма не коммутативна, кажется, нет способа привести `const_iterator` к обычному варианту.

**Но Майерс также и придложил решение к данной проблеме.**
Он предлагает использовать `advance`:
```cpp
Iter it(cont.begin());
std::advance(it, std::distance<decltype(cit)>(it, cit));
```
Явный шаблонный параметр тут указан, чтобы избежать неоднозначности при выводе типов, так как у `it` и `cit` они разные.

Проблема только в том, что фактически это `const_cast`, но за `O(n)` для неудачных контейнеров.

В свою очередь, к проблеме подтянулись и другие люди. 
Например поступило предложение от одного из разработчиков стандарта.
**Трюк Хинанта:**
```cpp
template <typename Container, typename ConstIterator>
typename Container::iterator
remove_constness(Container& c, ConstIterator it){
	return c.erase(it, it);
}
```
Идея в том, что начиная с `C++11`, удаление пустого диапазона позволено, оно не делает ничего и возвращает просто итератор для любого контейнера, вне зависимости от того, с каким итератором был вызван `erase`. Вернули `const_cast` за `O(1)`.
Беда в том, что это не работает для обратных итераторов и строк.

## Адаптация: обратный `range-based` обход
Задача - сделать адаптер `reverse_cont`, такой, чтобы работал цикл:
```cpp
for (auto &&elt : vec) 
// обойти в прямом порядке
for (auto &&elt : reverse_cont(vec)) 
// обойти в обратном порядке
```
### Реализация `reverse_cont`
```cpp
template <typename T> struct reversion_wrapper {
	T& iterable;
};

template <typename T> auto begin(reversion_wrapper<T> w) {
	return rbegin(w.iterable);
};

template <typename T> auto end(reversion_wrapper<T> w) {
	return rend(w.iterable);
};

template <typename T>
reversion_wrapper<T> reverse_cont(T&& iterable) {
	return { iterable };
}
```
### Обсуждение 
Это разительно отличается от полноценного `zip range`.
Тут мы по сути используем обычные итераторы, меняется только обёртка.
## Адаптация: `inserters`
Преобразование записи во вставку:
```cpp
std::vector<int> vec;

// тяжёлый способ
std::back_insert_iterator<std::vector<int>> bins(vec);

// лёгкий способ
auto bins = std::back_inserter(vec);

*bins = 1; 
// вставка элемента, как vec.push_back(1);

bins = 1; 
// тоже вставка элемента, как vec.push_back(1);
```
А что должен тогда делать `bins++`?
Ответ в том, что он практически ничего не должен делать, как и `operator*`, но они оба должны присутствовать, так как иначе этот тип нельзя было бы назвать итератором.
### Пример: кросс-копирование
Задача - скопировать содержимое списка `lst` в вектор `vec`:
```cpp
template <typename InpIter, typename OutIter>
OutIter cross_copy(InpIter fst, InpIter lst, OutIter dst){
	while (fst != lst) {*dst = *fst; ++fst; ++dst;}
	return dst;
}

std::list<int> lst = {1,2,3,4,5,6};
std::vector<int> vec;

vec.resize(lst.size());
cross_copy(lst.begin(), lst.end(), std::back_inserter(vec));
cross_copy(lst.begin(), lst.end(), 
	std::ostream_iterator<int>(std::cout, "\n"));
// система похожая, так как они оба - output iterators
```
## Виды адаптеров вставки для итераторов
- `std::back_inserter` для вставки в конец (предпочтительно)
- `std::front_inserter` для вставки в начало (можно попасть на асимптотику)
- `std::inserter` для вставки в произвольное место (шансы на так себе асимптотику увеличиваются)
```cpp
std::vector<int> v = {2,3,7,11};

auto it = std::find(v.begin(), v.end(), 3);
auto insit = std::inserter(v, it);

insit = 5; // теперь v = {2, 3, 5, 7, 11}; // мб ошибка?
```
