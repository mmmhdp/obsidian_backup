# Syntax
Левая ссылка, вспоминая то, как выглядит память с точки зрения C++, 
это второе имя для переменной, которое указывает на то же место в памяти, что и 
изначальный объект.
```cpp
int x = 13;
int &y = x;
```
# Rules
- Единожды взятую ссылку нельзя перевязать
```cpp
int x, y;
int &xref = x; // xref буквально алиас к x
xref = y; // т.е. <=> x = y;
```
- Ссылки прозрачны для операций, включая взятие адреса
```cpp
int *xptr = &xref; // т.е. <=> &x;
```
- Но! сами ссылки соответственно своего адреса не имеют, т.е. нам не удастся 
  создать указатель на память, которая содержит ссылку.
  Это логично, с учётом того, что семантически ссылка буквально прозрачный алиас, а значит её как бы адрес - это адрес того, на что она указывает, у неё самой его нет
```cpp
int &* xrefptr = &xref; // ошибка, нет указателя на ссылку на инт
int *& xptrref = &xptr; // всё ок, ведь ссылка на инт указатель уже есть, на указатель-то память где-то выделена!
```
- Правила константности тут упрощены, так как саму ссылку изменить нельзя, то const сразу говорит о том, что данные под ссылкой неизменяемые, вне зависимости от того, куда подставили const
```cpp
int const & cref_0 = x;
const int & cref_1 = x;
//cref_0 и cref_1 - константные ссылки на константные данные
int & ref = x
//ref - константная ссылка на изменяемые данные
```
# Usage
- Ссылка на объект в выражениях ведёт себя как сам объект. Т.е. она, как и в случае с 
  массивом, который деградирует (decay) к указателю на первый элемент, когда он используется как rvalue.
- Прокидывать в функции вместо указателей на тяжёлые объекты.
  Причина та же, но ссылка даёт куда больше гарантий, например, что объект не nullptr, ссылка же указывает на какую-то ВАЛИДНУЮ память.
	
  Но также мы не можем и менять ссылку! Т.е. фактически, нам не дают сломать указатель, при том, что под указателем мы всё также можем работать.
  Ссылка - это просто имя, в отличии от ячейки памяти, которой является указатель.
  ```cpp
  /*
  вот возможный пример того, как указатель даёт делать с 
  памятью всё, что угодно, в том числе, повредить её, сделав
  объект неконсистентным!
  */
  int foo(const int *p) {
	  int *t = p; delete p; return t;
  }

  // а вот со ссылкой такое нельзя провернуть
  int bar(const int &p) {
	  return p;
  }
  
  foo(nullptr); // с bar такое не прокатит
  ```

  Инвариант ссылки принадлежит не нам, её побитовое представление скрыто, 
  поэтому даже такое не возможно с bar()
```cpp
double d = 1.0;
int *q = *reinterpret_cast<int **>(&d)

foo(q); // будет работать, формально аргумент пролезет!
bar(q); // а вот это строго сохранит инвариант типа и работать не будет!
```
  
  И при этом, мы не добавляем уровни косвенности, он всё ещё один, как и при работе с указателями.
  
- Синоним для объекта с массивными именем
```cpp
void foo(BigBoi & b)
{
	int &internal = b.gut.smth[3].internal;
}
```
# Take into account
## Dangling refs
- Ссылки, также как и указатели, могут провиснуть.
  - Вернули из функции ссылку на временный объект - провисла
  - Жива ссылка на удалённую память - провисла
### Lifetime extension 
Константные ссылки (и только они) продлевают жизнь временных объектов!
```cpp
const int & lx = 0;
int x = lx; // ok

int foo();

const int & ly = 42 + foo();
int y = ly; // ok
```
Но не стоит соблазнятся, ссылка связывается со значением, а не со ссылкой, так что константная ссылка также успешно провиснет, если её вернуть из функции.
