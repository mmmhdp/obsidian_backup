Копирование это в основном способ инициализации:
```cpp
Copyable a;
Copyable b(a), c{a}; // прямое конструирование via ctor

Copyable d = a; // копирующее конструирование
```
А есть присваивание - это переписывание готового объекта:
```cpp
a = b; // присваивание

d = c = a = b; // присваивание цепочкой (правоассоциативно)
```
Т.е. копирование похоже на конструктор, а вот присваивание совсем не похоже.
# `Copy semantics`
Предыстория - обсуждение сгенерированных компилятором по дефолту методов пустого класса [[Empty class magic]].
Вопрос, а как выглядит эта генерация?

По умолчанию, конструктор и оператор присваивания реализуют:
- побитовое копирование и присваивание для встроенных типов и агрегатов
- Вызов конструктора копирования, если есть
```cpp
template <typename T> struct Point2D {
	T x_, y_;
/*
	Point2D(): default-init x_, default-init y_ {}
	~Point2D() {}
	Point2D(const Point2D & rhs): x_(rhs.x_), y_(rhs.y_) ; 
	Point2D & operator=(const Point2D & rhs){
		if (this == &rhs)
			return *this;
			
		this.x_ = rhs.x_;	
		this.y_ = rhs.y_;	
		return *this;
	}; 
*/
};
```
## Спецсмантика копирования (`RVO`)
Она состоит в том, что объект после копирования должен быть во всех смыслах эквивалентен тому объекту, из которого он и копировался.

Это становится более важным утверждением на фоне **семантики перемещения**([[Move semantics]]), которая по своей сути близка к копированию, но является нечто иным, так как там объект, из которого происходило присвоение остаётся не в спец-состоянии - он консистентен, но не валиден. Это значит, что такой объект можно удалить (т.е. его деструктор имеет возможность корректно отработать), но вот работать с этим объектом уже нельзя, так как его инваринты имеют право быть нарушенными.

`RVO - return value optimization`. Вот тут мы ещё раз убеждаемся, что конструктор копирования - это совершенно отдельная сущность, а не просто конструктор из объекта.

Дело в том, что фронтенд компилятора закладывается на семантику конструктора копирования, что позволяет ему, например, оптимизировать возращаемое значение из функции, не вызывая лишних копирований.

Рассмотрим вот такой пример:
```cpp
struct Foo {
	Foo() {
		std::cout << "ctor\n";
	}
	~Foo() {
		std::cout << "dtor\n";
	}
	Foo(const Foo & rhs) {
		std::cout << "copy ctor\n";
	}
};

foo bar(){
	Foo local_foo;
	return local_foo;	
}

int main (){
	Foo doo = bar();
	use(doo); // void use (Foo &);
}
```
Суть его в том, что в итоге на экране будет только:
```
ctor
dtor
```
И всё потому, что `local_foo` по семантике копирование является эквивалентны `doo` объектом, а раз он инициализирован дефолтным конструктором и сразу возвращается, компилятор прост напрямую инициализирует дефолтный объект в функции `main`. Без семантики копирования копирование было бы невозможно пропускать, так как в конструкторе копирования есть побочные эффекты, которые компилятор не может отбросить по правилу "`as if rule`". 

Исходя из этого логично, что у такого конструктора копирования должен быть стабильные интерфейс, который будет узнавать компилятор.

Основная его форма выглядит вот так:
```cpp
struct Copyable {
	Copyable (const Copyable& c);
};
```
Но, допустимо также принимать неконстантную ссылку, как угодно `cv`-квалифицированную ссылку или значение (`cv - const volatile` [[Functions and methods specifiers, modifiers, attributes]]).
# Недопустимые формы
`Шаблонный конструктор это никогда не конструктор копирования`:
```cpp
/*
	Тут всё нормально, класс шаблонный,
	а вот конструктор НЕ ШАБЛОННЫЙ (нет T)
	
	Поэтому вызов произойдёт и будет вызван 
	написанный нами конструктор,
	как бы мы того и хотели
*/
template <typename T> struct Copyable {
	Copyable(const Copyable& c){
		std::cout << "Hello";
	}
};

Copyable <void> a;
Copyable <void> b{a}; // на экране Hello
```

```cpp
// А вот теперь беда, напишем шаблонный конструктор копирования, 
// вернее попробуем это сделать

template <typename T> struct Coercible {
	template <typename U>(const Coercible<U>& c){
		std::cout << "Hello";
	}
};


Copyable <void> a;
Copyable <void> b{a}; 
/* 
	а теперь на экране ничего не будет
	дело в том, что теперь данная функция 
	будет распознана в качестве 
	функции перевода из одного типа в другой.
	
	Да, T = U является частным случаем,
	 но это для компилятора не важно,
	форма не совпадает, а значит от просто берет
	и генерирует конструктор копирования по умолчанию,
	раз мы его не определили, 
	поэтому на экране ничего и нет
*/

Copyable <int> c{a};
/*
	а тут компилятор сгенерирует конструктор копирования 
	по умолчанию для типа int, 
	т.е. на экране тоже ничего не будет 
*/
```
# Спецсемантика инициализации
Тут идея в том, что при инициализации, конструкторы определяют **неявное преобразование типа**, что и подразумевается в большинстве случаев.

Тут `42` с типом `int` преобразуется в аргумент с типом `MyString`.
```cpp
struct MyString {
	char * buf_; size_t len_;
	MyString (size_t len) : 
		buf_(new char[len]{}), len_(len) {}
};

void foo (MyString);

foo(42); // ok, MyString implicitly constructed
```
Но с другой стороны, это же порождает и проблему, так как в данном случае мы ничего такого не хотели, `int` может и отрицательные значения принять, да и вообще в данном случае такое преобразования типа завязано на выделение памяти, а значит дорогое.

Для решения данной проблемы, когда мы хотим убрать эту семантику, используется ключевое слово `explicit`. 

Но в общем случае, это экстрим и об этом надо помнить:
```cpp
struct MyString {
	char * buf_; size_t len_;
	explicit MyString (size_t len) :
		buf_(new char[len]{}), len_(len) {}
};

void foo (MyString);

foo(42); // fail! err: could not convert "42" from "int" to "MyString"
```
# Again `direct vs copy initialization`
- Важно понимать, что `explicit` конструкторы рассматриваются для прямой(`direct`) инициализации:
```cpp
struct Foo {
	explicit Foo(int x) {} 
	// блокирует неявные преобразования
};

Foo f{2}; 
// прямая инициализация, всё работает, вызывается наш конструктор

Foo f = 2;
/*
	FAIL! инициализация копированием будет 
	также отрезана из-за explicit,
	тут необходимо было бы 
	привести тип int к Foo во время вызова
	(но как бы вызова, тут ошибка компиляции),
	что мы делать как раз и запретили 
*/
```
В этом смысле инициализация копированием похожа на вызов функции.

Такжу, с учётом [[Operator type]], существует вообще говоря некая избыточность в возможностях преобразования
![[Pasted image 20251202112802.png]]
Собственно, возникает вопрос, а что будет при конфликте? Кого вызовут?
```cpp
struct Foo {
	Foo () {};
	Foo (const Bar &) { 
		std::cout << "Ctor Bar -> Foo" << std::endl
	};
};
struct Bar {
	Bar () {};
	Bar (const Foo &) { 
		std::cout << "Ctor Foo -> Bar" << std::endl
	};
	operator Foo () {
		std::cout << "Op Bar -> Foo" << std::endl};
		return Foo {};	
	}
};

int main () {
	Bar b;
	Foo f1{b};
	// direct-init, ctor
	// "Ctor Bar -> Foo"
	
	Foo f2 = b; 
	// copy-init, ctor vs op, op wins
	// "Op Bar -> Foo"
}
```
- Главное отличие `direct-init` от `copy-init` состоит в том, что они рассматривают разные `overload` сеты.
`direct-init` - рассматриваются все конструкторы, включая `explicit`, но только они.
`copy-init` - рассматриваются только `implicit` конструкторы, но зато вместе с ними входят и все остальные варианты, включая операторы `implicit` каста.
**Мда, но тут оказалось, что всё это не совсем так, и работает оно как описано до `14` стандарта включительно, а далее оказывается, начинается пробел между компиляторами, которые рассматривают в `direct-init` и функции преобразований тоже, т.е. фактически отличие overload сетов будет ещё меньше, т.е. по факту в лицо летит два "`Op Bar -> Foo`" на `17 +` стандартах. Проблема, как оказывается, известная (что игнорируется `copy elision`) и его хотят устранить.**
- Пользовательские преобразования тоже участвуют в перегрузке, они проигрывают стандартным, но выигрывают у троеточия
# Итог
В мире конструкторов спецсемантика существует тольку у конструктора копирования и приведения.

В мире операторов спецсемантика существует повсеместно.
