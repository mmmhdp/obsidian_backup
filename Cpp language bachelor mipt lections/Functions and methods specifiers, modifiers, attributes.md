**Обзор возможных спецификаторов и модификаторов повередения функции.**
# `Attributes`
Могут появиться в любой точке объявления, в зависимости от поведения аттрибута, так что при использовании стоит ещё раз оценить синтаксис для конкретного аттрибута, но важно понимать, ЧТО ОНИ НЕ ВЛИЯЮТ НА ОПРЕДЕЛЕНИЕ ТИПОВ И КОНФИГУРАЦИЮ МНОЖЕСТВ ПЕРЕГРУЗКИ 
ФУНКЦИЙ. 

По своей сути являются подсказками для компилятора о поведении и обрабатываются им же, позволяя решать некоторые проблемы языка без введения дополнительных keyword-ов или добавления нового смысла старым, что пораждает проблемы с обратной совместимостью.

Важно понимать, что аттрибуты могут быть использованы не только в контексте методов и фунций, а в целом применимы и в других сценариях, например в отношении переменных.
## Примеры с фукциями
```cpp
/* 
[[noreturn]] signals about a nonreturn nature of function,
which helpful if func suppose to throw or terminate only
*/
[[noreturn]] void f()
{
    throw "error";
    // OK
}
 
void q [[noreturn]] (int i) {
    // behavior is undefined if called with an argument <= 0
    if (i > 0)
        throw "positive";
}
 
// void h() [[noreturn]]; // error: attribute applied to function type of h, not h itself
 
int main()
{
    try { f(); } catch(...) {}
    try { q(42); } catch(...) {}
}

/*
[[nodiscard]] signals that return value of a given function
cannot be ignored and should be taken into account
*/
[[nodiscard]] int compute();

/*
[[deprecated]] no comments needed I guess
*/
[[deprecated("Use new_function instead")]]
void old_function();
```
## Пример с конструкциями языка
```cpp
/*
Тут как раз аттрибут решает проблему дизайна switch(), который по дефолту проваливается, что
на самом деле не является в действительности стандартным ожидаемым поведением в этой конструкции, 
а потому, если case не закончился break, компилятор предупредит о том, что вот тут switch с провалом по какому-то
case. Чтобы использовать диагностику, а также подчеркнуть свои намерения, что я прям хочу проваливаться вот тут, 
используется аттрибут [[falltrough]].  
*/
switch(x) {
    case 1:
        do_something();
        [[fallthrough]];
    case 2:
        do_something_else();
}
```
## Пример с переменными/функциями
Тут лукавлю, данный аттрибут можно применить и к вызову функции.
```cpp
/*
[[maybe_unused]] подавляет предупреждения о неиспользованных переменных 
или проигнорированных результатах вызова функции
*/
[[maybe_unused]] int temp = 42;
```

# `Specifier-seq`
Данные спецификаторы связаны тем, что они не являются частью типа самой функции, а являются спецификаторами её объявления.
## `Function specifiers`
- `inline`
- `virtual
- `explicit` (применим только к конструтору или операторам приведения к типу)
- `constexpr`
- `consteval`
## `Storage-class specifires` 
- `static`
- `extern` (почти никогда не используется для методов класса, чаще всего применим к внешним функциям)
## Friendship
- `friend`
# `Declarator` (`actual function type or signature`)
Данные спецификаторы особенны тем, что являются частью не только типа (все параметры функции и типы аргументов), но и сигнатуры функции (т.е. тех параметров функции, а также типы аргументов, по которому формируется множетсво перегрузки), а значит, каждый из них определяет
множество перегрузки (`overload set`), именно поэтому `const volatile` внесён отдельно, так как это не пересечение 
множеств `const` и `volatile` в смысле перегрузок, а отдельное подмножество.
## `cv-qualifiers`
Важно отметить, что данные модификаторы говорят нам ещё и о том, с каким объектами
класса может работать данный метод. 

Интересное начинается с понимания того, что ни один метод в стандартной библиотеке не аннотирован как `const volatile` и вообще почти никакие методы не аннотированы `const` или `volatile`. Т.е. вообще говоря, `cv` стандартный контейнер буквально почти ничего не способен делать.
- `const`
- `volatile`
- `const volatile`
## `ref-qualifiers`
- `&`
- `&&`
# `Exception specification`
Это часть типа с 11 стандарта, но не часть сигнатуры, т.е. перегрузить по `noexcept` нельзя.
(Просто к слову, можно изменить тип аргумента, добавив `noexcept`, тогда перегрузка возможна, но это по факту просто базовое правило, так как тогда изменился тип аргумента, но это не спецификатор самой функции, т.е. это не совсем то, о чём тут речь вообще идёт)
- `noexcept`
- `noexcept (expr)`
# `Override/final specifiers`
Данные спецификаторы не являются частью типа
- `override`
- `final`
# `Trailing return type`
Понятно, что это часть типа, но частью сигнатуры не является, т.е. перегружать нельзя.
